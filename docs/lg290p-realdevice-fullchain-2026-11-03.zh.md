## 2. 一键升级（2.2.3 → 3.0.0）

### 做法

```bash
rm -rf /root/ntrip-src
git clone --depth 1 https://gitcode.com/rampump/NTRIPserver.git /root/ntrip-src
cd /root/ntrip-src && bash update.sh
```

`update.sh` 以脚本自身所在目录为源码目录（`SRC_DIR`），所以必须先拿到新版本源码再执行。

## 7. 真机暴露的缺陷与修复

本节是这次测试最有价值的部分——五个问题里有四个是**只在真机上才会出现**的。

### 7.1 「中止」按钮必定 500（P1）

**现象**：点一键标定的「终止标定」，页面弹"服务器错误"，但任务其实停了。

```
api_calibration.py:315  ok, message, payload = calib.abort()
ValueError: not enough values to unpack (expected 3, got 2)
```

**根因**：`service.abort()` 的契约一直是 `(ok, message)` 两元组，`service.py` 内另外两处调用点
（CLI、看门狗）也是这么解的，只有 Web 接口多要了一个 payload。

**影响**：取消动作已生效（取消标记置位、模块会安全收尾），但用户看到 500 会以为没停下来而反复点，
在 SAVE/RESTART 阶段反复中止有打断收尾的风险。

**修复**：改为解两元组，快照仍由 `_snapshot_payload()` 单独取。
新增 `tests/test_contract.py::TestCalibrationApiUnpacking` 锁住契约（两元组 → 200，空闲 → 409）。
**复验证**：修复后 `POST /api/calibration/abort` 在空闲时返回 409（不再是 500）。

### 7.2 只读诊断被打断却谎报"模块可能停在中间配置上"

**现象**：探测 `/dev/ttyUSB0`（非 GNSS 串口）超时，随后升级重启，启动横幅写：

> 上次标定在「识别模块」阶段被中断（端口 /dev/ttyUSB0）。模块可能停在中间配置上，建议重新标定或先做一次只读诊断

**根因**：启动钩子不看任务类型，一律按"写操作被中断"措辞。但「识别模块」是只读诊断，
连波特率都不改，不存在"中间配置"。

**影响**：用户按提示去重标一轮，白跑；更糟的是这类误报会稀释真正的中断警告。

**修复**：`SerialLease` 增加 `action` 字段并落进 `lease.json`/快照；启动钩子按 action 分流，
只读动作改说"只读诊断不写模块，当前配置没有被改动，可以直接重新开始"。老租约没有该字段时按
stage（DETECT/OBSERVE）兜底。

### 7.3 「1005 播发偏差：NaN cm」（P1，出现在主路径）

**现象**：诊断结论写着"配置坐标与播发坐标一致"，紧接着一行 `1005 播发偏差：NaN cm`，
下面还跟一句 `下一步：配置坐标与 1005 播发值一致（最大轴差 0.00 mm）`。

**根因**：后端 `delta` 是对象 `{dx,dy,dz,max_axis,norm}`（单位 m），前端写的是
`(Number(delta) * 100).toFixed(2)`。`Number({...})` 恒为 `NaN`。

**影响**：这是"链路通不通"的唯一硬证据，显示成 NaN 等于把唯一的量化证据变成噪声；
更糟的是它与"一致"的结论自相矛盾，用户会怀疑整条链路。

**修复**：取 `delta.max_axis`，非有限值时显示占位符 `—`。
**复验证**：修复后同一诊断显示 `1005 播发偏差：0.01 cm`。

### 7.4 「丢字节数超过收到的行数」——单位错配导致的永久误报

**现象**：同一次诊断，绿色结论框里固定带一句
> 提示：丢弃字节数超过收到的行数；波特率可能不对，或串口线受干扰

**根因**：判据是 `noise > lines`，但 `noise` 计的是**字节**、`lines` 计的是**条数**。
基准站模式下串口上几乎全是 RTCM 二进制（一帧几百到上千字节），任何正常基站都会永久命中。

**影响**：一个永远为真的告警，等于没有告警；它还会把真正的波特率问题淹没掉。

**修复**：改为噪声字节占 **接收字节** 的比例（`rx_bytes`），超过 20% 才告警，并在文案里给出实际比例。
**复验证**：修复后同一次诊断不再出现该提示。

### 7.5 阶段流水 13 行全是同一个时间

**现象**：一次 2 分半的标定，阶段流水每一行的时间戳都是 `16:04:21`（任务开机时刻），
而页头写的是 `16:04:21 — 16:06:55`。

**根因**：前端每行取 `snap.started_at`，而后端从来没有下发过"当前阶段的进入时刻"。

**影响**：这个列表唯一的用途就是"看卡在哪一步、每步多久"，时间全一样就等于废了——
本次就是靠它才直观看到 `FIX_WAIT` 只花了 60 秒、而 `COLLECT` 花了 56 秒。

**修复**：后端 `_set_stage` 记录 `stage_at`（阶段变化时更新）并随快照下发；前端优先用它。
**复验证**：修复后流水为 `16:16:39 / 16:16:39 / … / 16:17:01`，逐阶段递增。

### 7.6 附带发现：契约测试入口漏跑 160+ 项（本地工程问题）

**现象**：一直以 `python -m tests.test_contract` 跑测试，输出恒为 `Ran 41 tests ... OK`。

**根因**：`tests/test_contract.py` 中间（第 433 行）有一份 `if __name__ == '__main__': unittest.main()`，
执行到这里就退出，后面的 160 多项（含全部标定契约、升级执行器契约）从未被执行过。

让 `python tests/test_contract.py` 与 `python -m unittest discover -s tests -t .` 两种跑法都成立。
全量现在是 **203 项**（1 项 skip）。

> 注：升级执行器自己用的是 `unittest discover`，所以线上升级验证一直是全量跑的，

## 11. 补充：评审本轮记录时发现的界面问题（3.1 已修）

英文版报告见 [lg290p-realdevice-fullchain-2026-11-03.en.md](lg290p-realdevice-fullchain-2026-11-03.en.md)。
下面四条都是"只有真机上手才会发现"的界面缺陷，单元测试覆盖不到，现已全部修复并各配了回归测试。

### 11.1 登录页没写默认账号

新装机器上没人知道该输什么。现在登录页有一条提示条写明 `admin` / `admin` 并提醒部署前改密；
口令一旦改过，提示条自动消失（`security.is_default_admin()`），不会继续教人用已经失效的口令。

### 11.2 「扫描串口」「读取挂载点」的候选列表满屏乱跑

两个原因叠在一起：

1. 填进原生 `<datalist>` 后**不会自动弹出**，必须再点一次输入框，用户以为按钮没生效；
2. 原生弹层的坐标由浏览器算，祖先只要有 `transform` 就会算错 —— 而本项目每张卡片都挂着
   `.fade-in` 动画，末帧 `transform: translateY(0)` 依然生效，于是列表出现在离输入框很远的地方。

修法：新增 `static/picker.js`，把 `list` 属性摘掉（原生弹层不再出现）、候选仍从原
`<datalist>` 读（写入候选的代码一行没改）、面板挂到 `<body>` 下用 `position: fixed` +
`getBoundingClientRect()` 现算坐标；扫完/读完自动展开，支持键盘、过滤，`disabled` 的候选项
保留显示但点不动。

### 11.3 三个出口卡片高度参差

上传 / 本地 Caster / 数传分别是 7 / 4 / 6 行，`align-items: start` 让每张卡各自撑高，
并排看就是三个不齐的框。现在统一拉伸到同一高度，底部说明贴底对齐。

### 11.4 波特率靠猜，没有问模块

先纠正一个常见的记错：LG290P 手册（§2.3.10 `PQTMCFGUART`）的 `<BaudRate>` 参数表列的是
**取值**（9600 / 115200 / 230400 / 460800 / 921600），**并没有给出厂默认值**——正文的 NOTE
只说「默认值没给的，用对应的 Get 命令查」。手册里所有示例都写 115200，但示例不等于承诺；
921600 是可选档位里最高的那一档，不是默认。另一版 LG290P(03)/LG580P(03) 规范甚至把范围写成
9600~4000000 连续区间，这意味着存在五档之外的合法非标值 —— **枚举永远覆盖不全，回读才是唯一可靠路径**。
本机真机回读结果：`UART1 115200 8N1`。

旧流程只能一档档试，每错一档白等 2 秒超时。现在：

- 驱动新增 `read_uart()`：LG290P 发 `$PQTMCFGUART,R`（应答
  `$PQTMCFGUART,OK,<Index>,<BaudRate>,<DataBit>,<Parity>,<StopBit>,<FlowCtrl>`），
  Unicore N4 发 `CONFIG` 收三行按口解析，LC29HBS 只有写命令，如实声明"不支持"；
- 结果既显示在硬件面板（`UART1 115200 8N1`），也按型号记进 `module_profiles.uart_baud`（schema v5）；
- 候选顺序改成：手填值 → 上次回读值 → 该型号 `DEFAULT_BAUD` → 其余厂商档位（降序）→ 全局兜底。

**首轮也不再盲试。** 这里踩了一个自欺的坑：`DEFAULT_BAUD` 早就声明了，但 `bauds()` 只做降序排序，
它压根没参与过排序——等于白写。纯降序的注释理由是"先用高的试，高的能通说明线材好"，听着合理，
可对首次插上的全新模块来说，唯一已知的信息恰恰是**手册示例里那个值**（LG290P 全部示例都是 115200）。
于是 921600 排第一，一块 115200 的模块要错 3 档才命中：**6 秒超时，一档不落**。
用户抱怨的"一档档试"并没有被解决，只是从低往高试换成了从高往低试。

现在 `DEFAULT_BAUD` 排第一（押注，押错照旧往下走，代价为零），其余仍降序：

```
lg290p  →  115200, 921600, 460800, 230400, 9600
```

本机收益：**首轮第一档就命中，0 次超时**（修复前 3 次 × 2 秒）；第二轮起还有回读值加持，
而且硬件面板能证明这个值来自模块，而不是来自某张表。

### 11.5 「一键标定好像没有选择模块型号」

其实有，在「设备」卡里，但页面上没有任何文字说明它改变什么，看起来像装饰。现在两条路都写清了：
**自动探测** = 依次向每个已注册型号各发一条识别命令（1~2 秒，顺带探测可选命令）；
**指定型号** = 只发一条，型号不符时直接报错并告出实际型号，绝不会把基站配置写进别的模块。

## 12. 第二轮真机：换插 LC29H(BS)（3.1.1 已修）

第一轮跑通之后，把 LG290P 拔掉、换到**另一个 USB 口**插上 LC29H(BS)，在同一台 Armbian 上继续
标定。这五个问题都不是"参数填错"，而是**流程层与驱动之间的契约缺口**，而且没有一个会在单元测试里
自己冒出来。

### 12.1 驱动少一个方法 = 一次 500

点「读取模块信息」直接报：

```
AttributeError: 'LC29HBSDriver' object has no attribute 'read_rtcm_config'
```

顺序上先说清楚：这不是"命令写错了"。诊断报告、备份、还原这套流程会**无条件调用**一组方法
（`read_rtcm_config`、`config_rtcm`、`get/set_message_rate`、`disable_survey_in`、
`get_svin_config`、`read_antenna_info`…），约定是"型号有这条命令就实现、没有就返回不支持"。
LG290P 与 N4 恰好都齐全，LC29H(BS) 缺了 5 个 —— 而**没有任何机制强制**实现它们，
于是"这个型号没有这条命令"这件本来很正常的事，变成了一次 HTTP 500。

修法分两层：

1. **基类兜底**：`BaseDriver` 给整张可选协议面（以及写路径上的 `save`/`reboot`/`set_mode` 等）
   提供默认实现，统一返回 `(False, '为什么不行', {'error': 'unsupported'})`。缺方法从此不是异常，
   而是一条可以显示给人看的原因。
2. **补齐真实现**：LC29H(BS) 的 5 条命令按厂商文档写出真身，而不是让兜底糊过去 ——
   - `read_rtcm_config()`：回读 `PAIR433/435/437`，并把"全局 Mode（0=MSM4 / 1=MSM7）"
     翻译成上层统一的 `msm_type`。顺手修掉一个静默错误：原来读的是 `data['mode']`，
     而 `request()` 只回 `{'fields': [...]}`，那个键永远是 None，页面上长期显示"RTCM 模式 unknown"。
   - `config_rtcm()`：`PAIR432` 只有 0/1 两档，用户选 MSM5/6 时**明确拒绝**，不做静默降级。
   - `get/set_message_rate()`：本型号只有 `PQTMSVINSTATUS` 与 `PQTMEPE` 两条可配，
     其余语句直接说"不支持"（省掉一次必然超时的下发）；`PQTMEPE` 的 `<MsgVer>` 是 **2** 不是 1。
   - `disable_survey_in()`：`PQTMCFGSVIN,W,0,0,0,0,0,0`（7 字段，不是 LG290P 的 8 字段）。
3. **契约测试**：`TestDriverProtocolSurface` 遍历所有已注册驱动，逐个断言 19 个方法都存在且
   返回三元组；`TestLc29hbsMissingCommands` 连**下发的命令体**一起断言，
   防止"返回 True 但什么都没发"这种更难查的写法。

### 12.2 「扫描串口」看起来没反应

换完 USB 口点扫描，界面上什么都没发生。实际是两个设计叠出来的错觉：

- 候选只写进 `<datalist>`，要**再点一次输入框**才会弹（3.1 加的自绘面板也只在输入框可交互时打开）；
- 失败信息写在页面**最底部的全局错误框**里，离那根输入框隔着好几屏。

现在扫描结果直接渲染成输入框下面的 chip（`#cal-port-chips`），结果与失败原因写在
`#cal-port-hint`；只有一个口时**自动填入**（换完线最想看到的就是"它认到了"）；
后端 `/api/serial_ports` 增加 `ok`/`count`/`error`，把"枚举失败"（权限、驱动）与
"确实没有设备"（线没插好）分开报。

### 12.3 「只测坐标」不该给单基站模块选

CORS 差分标定对 LC29H(BS) 是灰的（它没有流动站模式，这点是对的），但「只测坐标」还亮着 ——
而「只测坐标」恰恰**必须靠接收 CORS 改正数**才能算出本机天线位置。让单基站模块跑这条路径，
结果是采满整档、拿到一个**米级单点解**，然后作为"标定成功"显示出来。这是最坏的一种成功：
用户会把这个米级坐标写进基准站。

现在两边同时判：

- 前端 `computeLocks()`：已指定型号且 `dual_mode === false` → 锁掉「只测坐标」，并给出替代方案；
- 后端 `start_cors(measure_only=True)`：同样条件下直接 400（防止直接 POST 或旧缓存绕过）；
- **未指定型号时放行** —— 未知模块完全可能就是一台现成的流动站，那正是这条路径存在的理由。

### 12.4 换块模块，历史坐标就"没有了"

「只写已知坐标」里的「复用本机历史坐标」是灰的，提示"本机还没有这块模块的历史坐标"。
可是半小时前刚用 LG290P 在同一根天线上测出过坐标。

原因是复用来源被 `module_sn` 过滤了。这个判据的初衷是防止拿**别人家的天线**坐标写进来，
但它把"同一根天线换了块模块"这个最常见、最合法的场景一起挡了 —— 而程序本来就无法判断
天线有没有被挪动（那才是真正的风险），替用户判定只会挡住正确操作。

现在复用来源 = **库内最近一条**，不区分型号与 SN；页面把型号、SN、时间、经纬高与 ECEF
一并列出来，由人核对"是不是同一根天线"。同时把「先测一次再写入」的说明补全：
测坐标需要**流动站模块**，并从 CORS 或其他 NTRIP Caster 注入差分数据。

### 12.5 坐标必须两种形态都落库

不同来源给的坐标形态不一样：1005 里是 ECEF，NMEA / CORS 成果表 / 厂家界面多半是经纬高。
以前只有"ECEF → 经纬度"一个方向，反向缺失：只给经纬高时 ECEF 为空，复用那条记录就得现场再算一次，
而每次算的人不同就会漂。

现在 `store._normalize_record()` 两个方向都补：

| 输入 | 落库结果 |
| --- | --- |
| 只有 ECEF | 反算经纬高（原有行为） |
| 只有经纬高 | 正算 ECEF，并同步补 `arp_*`（这组数就是要写进模块的值） |
| 两者都有但不一致 | **以 ECEF 为准**重算经纬度并告警（ECEF 才是真正播进 1005 的那组） |

量化到 4 位小数（0.1 mm），与 RTCM 1005 的分辨率一致 —— 再细也播不出去，只会在库里留下对不齐的尾数。
实测往返误差：纬度 `9e-11°`、经度 `4e-10°`（约 0.01 mm 量级），远小于 1.1 cm 的标定精度。

一致性阈值取 5 cm：入口给的经纬度常常只有 7~9 位小数、或来自不同大地基准（CGCS2000 与 WGS84
差不到 1 cm），几毫米的差属于正常量化；超过 5 cm 就不是舍入了，那是两组来自不同地方的数被拼进同一行。

### 12.6 本轮验证

- 全量契约测试 **238 项通过**（上一轮 216 项，新增 22 项覆盖本轮五个问题）；
- `/api/calibration/options` 已无 `own_history`，`reuse_history` 返回库内最近一条
  （2026-11-02 11:59:06 / lg290p / SN 00006FE9326C3E41 / 25.2035236°,110.2774837°）；
- `external_rover` + `lc29hbs` → 400 并给出替代方案；不指定型号 → 202 放行；
- 坐标双向换算用**本轮真机实测的那组值**回归：由 `25.20352374°,110.27748337°,138.316 m`
  正算得 `-2001277.3805, 5416696.8658, 2699549.3066`，与设备回读值的差为 0.6 mm（4 位小数舍入）。
