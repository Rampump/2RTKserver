## 2. 一键升级（2.2.3 → 3.0.0）

### 做法

```bash
rm -rf /root/ntrip-src
git clone --depth 1 https://gitcode.com/rampump/NTRIPserver.git /root/ntrip-src
cd /root/ntrip-src && bash update.sh
```

`update.sh` 以脚本自身所在目录为源码目录（`SRC_DIR`），所以必须先拿到新版本源码再执行。

## 7. 真机暴露的缺陷与修复

本节是这次测试最有价值的部分——五个问题里有四个是**只在真机上才会出现**的。

### 7.1 「中止」按钮必定 500（P1）

**现象**：点一键标定的「终止标定」，页面弹"服务器错误"，但任务其实停了。

```
api_calibration.py:315  ok, message, payload = calib.abort()
ValueError: not enough values to unpack (expected 3, got 2)
```

**根因**：`service.abort()` 的契约一直是 `(ok, message)` 两元组，`service.py` 内另外两处调用点
（CLI、看门狗）也是这么解的，只有 Web 接口多要了一个 payload。

**影响**：取消动作已生效（取消标记置位、模块会安全收尾），但用户看到 500 会以为没停下来而反复点，
在 SAVE/RESTART 阶段反复中止有打断收尾的风险。

**修复**：改为解两元组，快照仍由 `_snapshot_payload()` 单独取。
新增 `tests/test_contract.py::TestCalibrationApiUnpacking` 锁住契约（两元组 → 200，空闲 → 409）。
**复验证**：修复后 `POST /api/calibration/abort` 在空闲时返回 409（不再是 500）。

### 7.2 只读诊断被打断却谎报"模块可能停在中间配置上"

**现象**：探测 `/dev/ttyUSB0`（非 GNSS 串口）超时，随后升级重启，启动横幅写：

> 上次标定在「识别模块」阶段被中断（端口 /dev/ttyUSB0）。模块可能停在中间配置上，建议重新标定或先做一次只读诊断

**根因**：启动钩子不看任务类型，一律按"写操作被中断"措辞。但「识别模块」是只读诊断，
连波特率都不改，不存在"中间配置"。

**影响**：用户按提示去重标一轮，白跑；更糟的是这类误报会稀释真正的中断警告。

**修复**：`SerialLease` 增加 `action` 字段并落进 `lease.json`/快照；启动钩子按 action 分流，
只读动作改说"只读诊断不写模块，当前配置没有被改动，可以直接重新开始"。老租约没有该字段时按
stage（DETECT/OBSERVE）兜底。

### 7.3 「1005 播发偏差：NaN cm」（P1，出现在主路径）

**现象**：诊断结论写着"配置坐标与播发坐标一致"，紧接着一行 `1005 播发偏差：NaN cm`，
下面还跟一句 `下一步：配置坐标与 1005 播发值一致（最大轴差 0.00 mm）`。

**根因**：后端 `delta` 是对象 `{dx,dy,dz,max_axis,norm}`（单位 m），前端写的是
`(Number(delta) * 100).toFixed(2)`。`Number({...})` 恒为 `NaN`。

**影响**：这是"链路通不通"的唯一硬证据，显示成 NaN 等于把唯一的量化证据变成噪声；
更糟的是它与"一致"的结论自相矛盾，用户会怀疑整条链路。

**修复**：取 `delta.max_axis`，非有限值时显示占位符 `—`。
**复验证**：修复后同一诊断显示 `1005 播发偏差：0.01 cm`。

### 7.4 「丢字节数超过收到的行数」——单位错配导致的永久误报

**现象**：同一次诊断，绿色结论框里固定带一句
> 提示：丢弃字节数超过收到的行数；波特率可能不对，或串口线受干扰

**根因**：判据是 `noise > lines`，但 `noise` 计的是**字节**、`lines` 计的是**条数**。
基准站模式下串口上几乎全是 RTCM 二进制（一帧几百到上千字节），任何正常基站都会永久命中。

**影响**：一个永远为真的告警，等于没有告警；它还会把真正的波特率问题淹没掉。

**修复**：改为噪声字节占 **接收字节** 的比例（`rx_bytes`），超过 20% 才告警，并在文案里给出实际比例。
**复验证**：修复后同一次诊断不再出现该提示。

### 7.5 阶段流水 13 行全是同一个时间

**现象**：一次 2 分半的标定，阶段流水每一行的时间戳都是 `16:04:21`（任务开机时刻），
而页头写的是 `16:04:21 — 16:06:55`。

**根因**：前端每行取 `snap.started_at`，而后端从来没有下发过"当前阶段的进入时刻"。

**影响**：这个列表唯一的用途就是"看卡在哪一步、每步多久"，时间全一样就等于废了——
本次就是靠它才直观看到 `FIX_WAIT` 只花了 60 秒、而 `COLLECT` 花了 56 秒。

**修复**：后端 `_set_stage` 记录 `stage_at`（阶段变化时更新）并随快照下发；前端优先用它。
**复验证**：修复后流水为 `16:16:39 / 16:16:39 / … / 16:17:01`，逐阶段递增。

### 7.6 附带发现：契约测试入口漏跑 160+ 项（本地工程问题）

**现象**：一直以 `python -m tests.test_contract` 跑测试，输出恒为 `Ran 41 tests ... OK`。

**根因**：`tests/test_contract.py` 中间（第 433 行）有一份 `if __name__ == '__main__': unittest.main()`，
