## 0. 一页结论

| 决策点 | 结论 | 一句话理由 |
| --- | --- | --- |
| **形态** | 独立页面 `/calibrate`（登录可见），配置页串口卡片下方只放一个入口链接 | 配置页是"一次 POST → 保存 → 重启"的语义，标定是"长事务 + 实时状态 + 可取消"，生命周期不兼容 |
| **串口怎么拿到** | 串口租约（Port Lease）：请求数据面让位 → 独占 → 归还 → 恢复 | 复用现成的 `restart_event` / `run_once` 语义，不需要改数据源代码 |
| **对主程序的侵入** | 主流程 **3 行 gate** + `state` 里 **1 个 Event** + `app.py` **1 行注册** + 模板 **1 处入口** | 热路径（`distribute` / `rtcm_parser` / `serial_source` / `outlets`）**一行不改** |
| **代价** | 标定期间数据面停服：写历史坐标 ≈ 20–40 秒；Survey-in 10–60 分钟；CORS 标定 5–15 分钟 | 模块在流动站模式下物理上不输出 RTCM，这是硬件约束，不是实现缺陷 |
| **失败兜底** | 任意路径结束都归还租约；线程崩溃由看门狗兜底；断电由启动钩子标记"上次被中断" | 宁可让用户重来一次，也不能让主程序永久卡在"数据面不启动" |
| **数据落盘** | 独立 `calibration.db`，不进 `settings` 表 | 标定结果是资产，配置是配置；`reset_config.py` 只应当清配置 |

**一句话架构**：一个页面、一个工作线程、一个状态机、一张租约；标定在"数据面让位"的窗口里
自己玩自己的串口，结束后把窗口还回去。

## 0.5 需求整理（口述 → 可执行条目）

这一章只做一件事：把"我想要一键把模块设成基准站"这句话，拆成能被实现、能被验收、
能被测试的条目。后面所有章节都从这一章派生。

### 0.5.1 这个功能在解决什么

一句话：**模块出厂时不知道自己在哪。**

RTK 基准站播出去的 RTCM 1005/1006 里带的是"我站在哪个 ECEF 坐标"，流动站拿这个坐标
去反算自己的位置。所以基准站坐标错了多少，**所有流动站的绝对位置就错多少**——这不是
精度问题，是坐标系原点问题。1 米的基准站坐标误差，会让下游每台流动站整体平移 1 米。

而模块本身只有单点定位（几米级），直接把它设成基准站，播出去的坐标就是几米级误差的。
所以必须有一步"把这个天线的相位中心点测准"的动作，这就是标定。

```
单点定位（米级）  ──需要外部高精度参考──▶  准确 ECEF（厘米级）  ──写入──▶  可信的基准站
                        ↑
               CORS 差分 / 模块自收敛 / 别人的测量结果
```

### 0.5.2 拿到坐标的五条路径（横向对比，决定 UI 上给几选一）

| # | 路径 | 需要网络 | 需要额外硬件 | 典型精度 | 耗时 | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| A | **CORS 差分 + 滤波**（本方案主线） | 要（公网 + 账号） | 无（双模模块） | 厘米级（2–5 cm） | 5–15 min | 有网、有账号、追求精度 |
| B | **复用历史 ECEF** | 不要 | 无 | 等于上次的精度 | 20–40 s | 天线没动过（最常见） |
| C | **模块 Survey-in 自收敛** | 不要 | 无 | 亚米级（0.3–2 m） | 10–60 min | 野外无网 |
| D | **外部流动站测完再换模块** | 要（走 A） | 要一台流动站 | 厘米级 | 10–20 min + 拔插 | 纯基准站模块（LC29HBS） |
| E | **手工输入已知坐标** | 不要 | 无 | 取决于来源 | 20 s | 已知点位（如已测过的墩台） |

UI 上不需要把这五条平铺给用户，而是**按模块能力 + 用户是否勾选历史坐标**收敛成 2–3 个可选，
其余灰掉或折叠（§11.1）。但底层五条路径都必须实现，因为 A/C/D 分别对应三种硬件形态。

### 0.5.3 三种模块形态 → 三条主流程

| 形态 | 代表型号 | 能否自己跑流动站 | 主流程 | 关键约束 |
| --- | --- | --- | --- | --- |
| **A 双模** | LG290P / LG580P / LG680P | ✅ | 切流动站 → 测 → 切回基准站 → 写坐标 | 两次模式切换都要 保存+重启+回读 |
| **B 纯基准站** | LC29HBS | ❌（无 `PQTMCFGRCVRMODE`） | 借用一台流动站测 → 拔掉 → 换回目标模块 → 写坐标 | 唯一需要**人工拔插**的流程 |
| **C 未知** | 任意 | ❓ 只能靠数据类型判断 | 按输出判定：NMEA→可测；RTCM→不可测 | 不能假设存在任何命令，只能"能测就测，测完能写就写" |

判据不看用户选了哪个下拉框，而看 **`VERNO` 返回的固件串 + 能力矩阵**（§5.3）。
用户选错型号时按"检测结果优先、但告知差异"处理（§5.2）。

### 0.5.4 界面：四行控件 + 一个状态区

对齐"先扫串口 → 选串口 → 选模块 → 填 CORS → 勾历史坐标 → 开始"这条口述顺序：

| 行 | 控件 | 数据来源 | 交互要点 |
| --- | --- | --- | --- |
| ① 串口 | 下拉 + 「扫描串口」+ 波特率 | `GET /api/serial_ports`（已存在，直接复用） | 只列 `/dev/ttyUSB*` `/dev/ttyACM*` `/dev/ttyS*`；标定中禁用；选中后显示"该口当前是/不是数据源" |
| ② 模块 | 下拉：`LG290P 系列（双模）` / `LC29HBS 系列（纯基准站）` / `手动输入型号` / `未知·自动识别` + 右侧小字 | 预设清单来自驱动注册表（可扩展），不是硬编码在模板里 | 选完立刻调整 ③ 的可选项（纯基准站不能选 CORS）；手输型号时仍以 `VERNO` 实测为准 |
| ③ CORS | 地址 / 端口(2101) / 用户名 / 密码 / 挂载点下拉 + 「读取挂载点」 | `POST /api/sourcetable`（已存在） | 口令打码显示；只读挂载点不建长连接；VRS 依赖 GGA 的提示放在这一行下方 |
| ④ 历史坐标 | 复选框 + 坐标卡（X/Y/Z、时间、精度、来源、模块 SN）+ 右侧小字 | `calibration.db`（同 SN 优先，其次同串口/同位置） | 未勾选才走完整测量；勾选后跳过测量直接写 |
| ⑤ 操作区 | 「开始一键标定」/「终止标定」/ 进度条 + 步骤文本 + 已用时 + 实时坐标 | 轮询 `GET /api/calibration/status` | 每步显示"正在做什么 + 上一步结果"，失败显示原因 + 已回退到哪 |

两句提示文案按原话保留（它们直接决定用户会不会误用）：

> 仅基准站模块无法自身跑流动站标定，需先外接流动站模块测量天线坐标；若天线位置未移动，
> 可复用历史 ECEF 坐标直接写入。

> 仅当天线位置未移动、未更换天线时可复用；移动天线或更换天线后必须重新标定。

### 0.5.5 形态 A（双模 + 未勾历史坐标）逐步拆解

把口述的"先切流动站 → 检查 GGA → 连 CORS → 等固定解 → 滤波 → 存库 → 写坐标 → 校验"
固化成带校验点的 12 步。**每一步都有回读/观测判据，不靠 OK 应答**：

| 步 | 动作 | 判据（必须实测） | 超时 | 失败去向 |
| --- | --- | --- | --- | --- |
| S1 | 打开串口，清缓冲，静默 300 ms | 无残留帧 | 1 s | 换波特率重试 |
| S2 | `VERNO` 识别型号 | 固件串匹配所选系列 | 2 s | 提示不符，让用户选继续/中止 |
| S3 | `SN` + `UNIQID` + `CFGRCVRMODE,R` | 拿到 SN；模式∈{1,2} | 2 s | 失败则降级为"只读诊断" |
| S4 | 备份当前模式与 SVIN 配置 | 已落盘 `calibration_backup` | 3 s | 失败不阻断（仅少了还原能力，需告知） |
| S5 | 切流动站 → 保存 → 重启 → 回读模式=1 | **回读值 == 1** | 10 s | 重试 2 次 → 失败终止 |
| S6 | 配 GGA 1 Hz、FIXRATE 1000 ms，回读 | 回读速率 == 1 | 3 s | 重试 1 次 |
| S7 | 观测 GGA：连续 3 条且坐标非空 | 帧有校验和、lat/lon 在合法域 | 30 s | 无 GGA → 启软件生成（§6.2） |
| S8 | 连 CORS（NTRIP），按 1 Hz 上报 GGA | `ICY 200 OK` 且 10 s 内有 RTCM | 15 s | 按错误码分类提示（§4.5 / §6.1） |
| S9 | 注入 RTCM 到模块，同时读回 NMEA | 写入成功；GGA 质量位开始变化 | 全程 | 写失败 → 重连 |
| S10 | 等固定解准入：质量=4、星数≥12、PDOP≤2.0，连续 30 s | **GGA/GSA 实测**（§7.2） | 10 min | 超时提示查天线/CORS |
| S11 | 采集并滤波：1 Hz → 3σ → 三轴卡尔曼 | 达到时长 或 连续 60 s 三轴 σ≤2 cm | 30 min | 用户可选"用当前值" |
| S12 | 停 CORS → 写 `CFGSVIN,W,2` → 回读偏差 ≤1 mm | 回读 X/Y/Z 与写入值一致 | 10 s | 重试 1 次 → 失败保留流动站 |
| S13 | 切基准站 → 配 1005/1033/MSM → 保存 → 重启 → 回读 | 回读模式=2、坐标一致 | 15 s | 保存失败 → 回写旧值（§8.4） |
| S14 | 解 1005 比对；确认输出是 RTCM 而非 NMEA | 偏差 ≤0.05 m 且 30 s 不断流 | 10 s | 0.05–0.5 m 警告；>0.5 m 失败 |
| S15 | 落库 + 注入 1033/STR 描述 + 归还租约 | 写库返回主键 | 2 s | 不阻断，记警告 |

**S12 与 S13 的顺序不能反**（§8.1）：先写坐标再切模式。反过来的话，一旦写坐标失败，
模块已经停在"基准站 + 坐标 0,0,0"，播出去的是一个在原点（几内亚湾）的基准站，
所有流动站会被带偏几千公里。

### 0.5.6 形态 B（纯基准站，两段式）

```
第一段（借流动站）
  提示：请插入流动站模块 → 用户确认 → 重新枚举串口 → 走 0.5.5 的 S1–S11
  → 得到 ECEF → 落库（记 module_sn = 流动站 SN，但 station_sn 记为待写目标）
  → 进入 WAIT_SWAP（不计超时，落盘，可关页面）

第二段（写目标模块）
  提示：请断电，更换为目标基准站模块（禁止热插拔）→ 用户点「已更换」
  → 重新枚举 + 识别（若 SN 与第一段相同 → 提示"检测到的仍是同一块模块"）
  → 从库取坐标 → S12–S15（无模式切换命令时跳过 S13 的切模式，只做保存+重启）
```

要点：**第二段完全不依赖第一段的串口状态**。拔插后旧 fd 已失效，必须重新 open；
这也是整个方案里唯一"允许串口消失一段时间"的地方，所以 `WAIT_SWAP` 期间租约仍持有，
但心跳改为"用户操作驱动"（用户不点就一直等，看门狗不判超时）。

### 0.5.7 形态 C（未知模块）

```
打开串口 → 静默 5 s（不发任何命令）→ 统计字节构成
├─ 有 NMEA、有 GGA        → 当流动站用：直接走 CORS 标定
├─ 有 NMEA、无 GGA        → 软件生成 GGA 再走（精度标注为单点级）
├─ 只有 RTCM（≥3 个 CRC 正确帧） → 判定已在基准站模式 → 不能测 → 给三条出路：
│     ① 换流动站模块；② 手工输入已知 ECEF；③ 用历史坐标
├─ NMEA + RTCM 混合       → 以"是否有 GGA"为准；无 GGA 按基准站处理并提示
└─ 全噪声                 → 提示波特率/供电（换档重试，§5.2）
```

未知模块**测完不一定能写**：没有命令集就写不进去。此时分两种收尾：
- 若 `VERNO` 意外匹配到已知驱动 → 走 S12–S15；
- 否则只落库，提示"坐标已保存，请更换为可配置的基准站模块后写入"（这条口述里明确要求）。

### 0.5.8 形态 C 之外：Survey-in（无网可用，全形态支持）

不管模块是双模还是纯基准站，只要它有 `CFGSVIN`，就能让**模块自己**收心：

```
切基准站 → CFGSVIN,W,1,<次数>,<精度>,0,0,0[,<距离>] → 开 PQTMSVINSTATUS 1Hz
→ 轮询 Valid=2 且 Obs≥次数 且 MeanAcc≤阈值 → 保存 → 重启 → 1005 校验 → 落库
```

它是 LC29HBS 唯一不需要外接流动站的路，也是现场无网时的唯一出路。
代价是精度只有亚米级，且耗时长（10–60 min），UI 必须和 CORS 的厘米级用不同颜色区分。

### 0.5.9 口述里我做了取舍的 6 处（请你重点看这几条）

| # | 口述原话 / 模糊点 | 我的处理 | 理由 |
| --- | --- | --- | --- |
| 1 | "读取它发送有没有发送 gga 数据…如果没有就从 nmea 提取地址生成 gga" | **不"等待 N 秒再看有没有"**，而是"3 条 GGA 或 5 秒内无 GGA 即启生成器"，且原生 GGA 一旦出现就自动切回透传 | 等太久浪费时间；且部分模块 GGA 速率是 0.2 Hz，硬等会误判为"没有 GGA" |
| 2 | "监控模块的固定解模式…读取它固定解的精确地址 ecef 坐标" | 模块**不直接输出 ECEF**，固定解只体现在 GGA 的经纬高 + 质量位。所以 ECEF 由程序从 GGA 换算（§7.1），再对 ECEF 做滤波 | NMEA 里没有 ECEF 字段；1005 是基准站模式才有的，流动站模式拿不到 |
| 3 | "采用滤波算法把这个位置读取出来" | 滤波做在 **ECEF 三轴独立**上，不是经纬度上 | 经纬度在极点/跨经线有奇异；且 ECEF 是各向同性的直角坐标，三轴独立卡尔曼成立 |
| 4 | "比如3分钟或者5分钟或者是10分钟" | 做成**时长 + 稳定度双终止**：到时长 或 连续 60 s 三轴 σ≤2 cm，先到先停 | 只按固定时长会在已经收敛后白等；只按 σ 会在信号差时永远不停 |
| 5 | "利用已久原来已经测量好的 ecef 坐标" | 匹配顺序：**同 SN 优先 → 同串口历史 → 同位置（±50 m）最近一条**，界面上必须显示这条记录是"哪块模块、什么时候测的" | 只看"最新一条"会在多台设备间串味；只按 SN 则在换模块后查不到 |
| 6 | "看一下模块运行的状态是否输出的是 rtcm 数据" | 作为**最终校验之一**，但不作为唯一判据：还要解 1005 比对坐标 | 只要模块在基准站模式就会出 RTCM，哪怕坐标是 0,0,0 也照出。只看"有 RTCM"会把错误当成功 |

另外统一两个用词：口述里的 "COS / CES / 流通站" 在文档里统一为 **CORS** 与**流动站**（Rover）。

## 1. 为什么必须先解决"串口独占"（原理层，决定了整个架构）

### 1.1 Linux tty 不排他

`/dev/ttyUSB0` 这类字符设备**允许多次 open**，内核不会拒绝第二个读者：

```
进程 A（数据源线程）   open(/dev/ttyUSB0) → fd 5
进程 B（标定线程）     open(/dev/ttyUSB0) → fd 9   # 照样成功
```

两个 fd 共享同一个 tty 的输入缓冲。谁先 `read()` 谁就吃掉那段字节，**没有"复制一份"的语义**。
这不是"可能出问题"，是必然出问题，而且表现为随机丢数据。

### 1.2 三个必然后果（都是线上会看到的症状）

| 后果 | 触发方式 | 用户看到的现象 |
| --- | --- | --- |
| **命令被当数据转发** | 标定发的 `$PQTMVERNO*58` 应答 `$PQTMVERNO,...` 被数据源线程读到，`distribute()` 原样扇出 | 下游 Caster / 移动站收到 NMEA 垃圾，RTKLIB 报 "invalid message"，本地 Caster 源列表里的消息类型被污染 |
| **RTCM 帧被撕成两半** | 标定线程的 `read()` 抢走了半帧 RTCM | 帧头在 A、载荷在 B，两边都解不出帧 → 主链路断流、CRC 告警 |
| **模式被改，下游不知道** | 标定把模块切到流动站模式（不再输出 RTCM） | 本地 Caster 客户端连接还在，但永远等不到数据，表现为"连上了但没差分" |

第二条尤其隐蔽：`extract_rtcm_frames` 会跳过一个字节重新同步，**看起来只是"偶尔丢一小段"**，
排查成本极高。所以本方案的第一条铁律是：

> **同一时刻，整个系统只有一个持有者能对这块串口做 read/write。**

### 1.3 三条候选路线对比

| 路线 | 做法 | 优点 | 致命问题 | 判定 |
| --- | --- | --- | --- | --- |
| **A. 在线共享（tap + 命令队列）** | 在 `upload_via_serial` 循环里插"只读 tap"和"命令 drain" | 热路径在线，下游几乎不断流 | 标定要**长时间独占读**（等 ACK、等 SVIN 状态、等 30 秒固定解），插进数据源循环等于把数据源线程改造成标定线程；CORS 注入的 RTCM 也会混进 `distribute()` 发给下游；出错时的回滚逻辑比新写一个模块还长 | ✗ |
| **B. 独立进程 + flock** | 像升级执行器那样 `systemd-run` 拉起一个进程，用文件锁保证唯一 | 与主进程彻底隔离，崩溃互不影响 | 需要跨进程回传全部状态、进度、日志；ARM 小板上多一份 Python 解释器常驻；调试成本高。**升级场景是必要的（要替换自身），标定不是** | ✗ 过度设计 |
| **C. 数据面让位 + 进程内租约** | 请求主循环暂停数据面 → 串口自然关闭 → 标定独占 → 结束后恢复 | 复用现成 `restart_event`/`run_once` 语义；热路径零改动；Web 全程在线；单进程内状态共享，无需序列化 | 标定期间下游必然断流（但 A 方案实际也做不到不断流） | ✓ **采用** |

### 1.4 为什么不做进配置页的"串口模式"区块

用户的原始诉求是"可以在配置页串口模式下添加，也可以单独做个页面"。评估后建议**独立页面**：

1. **表单语义冲突**：配置页的每个卡片结尾都是"保存并重启"按钮，提交即写库 + `restart_event`。
   标定需要的是"开始 → 轮询 → 停止"，中间还要接受参数修改但**不**写库。
2. **并发风险**：标定进行中用户点了配置页的"保存并重启"，`restart_event` 会让主循环
   在租约未释放时重启数据面 → 直接违背独占铁律。独立页面可以从设计上禁止这种交叉操作。
3. **信息密度**：标定要展示时间线、卫星数、PDOP、解状态、σ 收敛曲线、日志尾，塞进配置页
   会把已经 400 行的 `config.html` 撑爆。
4. **入口仍放在配置页**：在"数据源 → 串口模式"卡片下方加一行链接「需要精确标定天线坐标？
   → 打开一键标定」，这样"串口模式下"的上下文没丢。

**依赖方向铁律**：`calibration → core/outlets/sources`（只读复用）；
`core/outlets/sources` **绝不反向 import calibration**。
这条用契约测试锁死（见 §15.1），因为它决定了"标定模块整个删掉，主程序照常跑"。

### 2.2 线程模型

| 线程 | 数量 | 职责 | 生命周期 |
| --- | --- | --- | --- |
| `calib-worker` | 1 | 跑状态机；所有串口读写、CORS 收发、滤波都在这里 | 任务开始时创建，任务终止即退出 |
| `main`（既有） | 1 | 租约期间跳过 `run_once()`，做心跳看门狗 | 常驻 |
| Web（既有） | N | 只读快照、下发指令 | 常驻 |

**刻意不新增第二条线程**：NTRIP 的"收 RTCM"和"发 GGA"看起来是两个节奏，但用
`socket.settimeout(0.2)` 的单线程轮询就能同时做（先 `recv`，超时即处理"该发 GGA 了"）。
两条线程共享一个 socket 反而要加锁，且 ARM 单核上纯属浪费。

### 2.3 与主程序的 4 个接缝（全部改动清单）

| # | 文件 | 位置 | 改动量 | 为什么必须改 |
| --- | --- | --- | --- | --- |
| 1 | `rtkserver/core/state.py` | 单例区 | +3 行 | 新增 `calibration_hold = threading.Event()` 与 `calibration_beat = 0.0`（心跳时间戳） |
| 2 | `rtkserver/core/lifecycle.py` | `main()` 的 `while` 循环顶部 | +6 行 | 租约期间跳过 `run_once()`，并对心跳做超时兜底 |
| 3 | `rtkserver/web/app.py` | `create_app()` 注册区 | +1 行 | `api_calibration.register(app)` |
| 4 | `templates/config.html` | 串口卡片底部 | +5 行 | 一个入口链接 |

除此之外**没有任何既有文件被修改**。特别是下列"看起来需要改其实不需要"的位置：

- `distribute()` —— 不改。标定时数据面已停，根本不会有数据流。
- `serial_source.upload_via_serial()` —— 不改。它靠 `thread_exit_event` 正常退出，`run_once` 的
  `finally` 会 `join(5)` 并关掉 `ser`。
- `rtcm_parser` —— 不改。1005/1033 的解码复用它的 `crc24q`，但标定有自己的轻量解码器
  （因为解析线程属于"数据面"，此刻已停，不能让标定去往全局 `rtcm_buffer` 里塞东西）。
- `config.py` / 数据库结构 —— 不改。标定只用独立的 `calibration.db`。

### 2.4 一行改动长什么样（示意，非最终代码）

```
while not state.shutdown_event.is_set():
    if state.calibration_hold.is_set():          # ← 新增
        _calibration_watchdog()                  # ← 新增：心跳超时则强制解除
        interruptible_sleep(1, state.shutdown_event)
        continue
    cfg = get_config()
    ...
```

这 6 行的语义是：**"有人在用串口，这轮先不起数据面"**。没有它，`run_once` 的 `finally`
一退出，`main` 立刻会再起一轮，把串口抢回去。

## 3. 核心机制一：串口租约

### 3.1 数据结构

内存里（`service._lease`）：

| 字段 | 含义 |
| --- | --- |
| `port` / `baud` | 目标串口与波特率 |
| `stage` | 当前阶段（与状态机同步） |
| `held` | 是否已独占 |
| `acquired_at` | 取到时刻 |

落盘（`.calibration/lease.json`，原子写：写临时文件 + `os.replace`）：

| 字段 | 用途 |
| --- | --- |
| `port` / `baud` | 进程重启后知道上次动的是哪个口 |
| `stage` | 上次停在哪个阶段 → 决定"模块可能处于什么状态" |
| `pid` | 判定持有者是否还活着 |
| `heartbeat` | 每 2 秒更新；看门狗据此判定"线程死了但 gate 没清" |
| `firmware` / `model` / `sn` | 中断后仍能告诉用户"上次是在哪块模块上操作的" |

**为什么落盘**：这是本方案唯一能防住"断电后模块处于半配置状态"的手段。
进程重启后内存全丢，但 `.calibration/lease.json` 还在，页面就能明确说：
"上次标定在 `SAVE` 阶段被中断，模块的 NVM 可能只写了一半，建议重新标定或直接用历史坐标覆盖。"

### 3.2 让位时序（acquire）

| 步 | 动作 | 判据 | 超时 | 失败处理 |
| --- | --- | --- | --- | --- |
| 1 | 前置校验：无进行中任务；`radio_port != 目标口`；`serial_port` 允许等于目标口 | 全部满足 | — | 立即返回明确原因，**不改任何状态** |
| 2 | 写 `lease.json`（stage=`PREPARE`） | 文件可写 | 2s | 失败 → 磁盘满/权限问题，终止 |
| 3 | `state.calibration_hold.set()` | — | — | — |
| 4 | `state.restart_event.set()` | — | — | — |
| 5 | 等 `state.worker_thread is None` | 数据源线程已退 | 8s（每 100ms 查） | 超时 → 判"数据面未能让出串口"；清 gate；提示"数据源线程仍在读取串口，请稍后重试（若反复出现请重启服务）" |
| 6 | 反复尝试打开串口 | open 成功 | 10 × 200ms | 超时 → 说明 fd 还没真正释放或权限不足；提示具体 errno（Permission denied / Device or resource busy） |
| 7 | `reset_input_buffer()` + 丢弃前 300ms 的残帧 | — | 300ms | 忽略异常 |
| 8 | 置 `held=True`，首次心跳 | — | — | — |

**第 5 步的 8 秒是有依据的**：串口线程的 `read()` 有 `timeout=1`，最坏 1 秒内返回；
`run_once` 的 `join(5)` 再加 5 秒；剩下 2 秒余量。超过 8 秒说明线程卡在别的地方
（例如 `detect_serial` 正在做 11 档波特率扫描，最坏 2 秒 × 11），此时必须放弃而不是硬等。

### 3.3 归还（release）

归还必须**幂等**，且放在 `try/finally` 的最外层：

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 关闭串口 fd | 任何异常都吞掉（fd 可能已经因拔线失效） |
| 2 | 若模块仍处于"流动站/未知"状态且用户没要求保留 → 尽力切回原模式 | 尽力而为，失败只记日志（见 §14 第 16 条） |
| 3 | `lease.json` 写终态（`DONE`/`FAILED`/`ABORTED`/`INTERRUPTED`） | 保留 24 小时供页面回显，之后清理 |
| 4 | `state.calibration_hold.clear()` | **必须在置 restart 之前**，否则主循环看不到释放 |
| 5 | `state.restart_event.set()` | 唤醒主循环立即恢复，不等 10 秒轮询 |
| 6 | 记录耗时、结果、错误原因到 `calibration.db` | 失败也记，便于统计"哪一步最容易挂" |

### 3.4 心跳与看门狗（防"线程死了 gate 卡住"）

这是整个方案里**最容易被忽略、后果最严重**的一环：如果标定线程因为未捕获异常死了，
而 `calibration_hold` 还置着，主程序会永久停在"数据面不启动"——用户看到的是
"网页能开、设备不转发数据"，且没有任何报错。

设计：

- 标定线程每 2 秒更新 `state.calibration_beat = time.time()`；
- `main()` 在 gate 分支里检查：`now - beat > 30` 且 `lease.stage` 不是终态 →
  强制 `hold.clear()` + `restart_event.set()` + `logging.error(...)`；
- 为什么是 30 秒而不是 5 秒：Survey-in 阶段单次等待就是 1 秒级，滤波循环里也可能
  因为 `sock.recv` 卡 20 秒（NTRIP 读超时），阈值太紧会误杀正常任务。

### 3.5 进程重启/断电后的残留判定

在 `state.hooks['startup']` 里挂一个 `calibration.on_startup()`（**复用现有钩子机制，
不需要再改 `main()`**）：

1. 读 `lease.json`；
2. `stage` 是终态 → 什么都不做（正常历史记录）；
3. `stage` 非终态 → 说明上次被硬中断：
   - 把记录标为 `interrupted`，写入 `calibration.db`；
   - 在内存里置 `state.calibration_interrupted = {stage, model, sn, at}`；
   - **不自动改动模块**（此刻串口还没被打开，任何"自动修复"都是盲操作）；
4. 页面打开时若发现该标记，顶部显示一条黄色横幅（内容见 §14 第 17 条）。

### 3.6 与数传出口、串口扫描的关系

| 场景 | 处理 |
| --- | --- |
| `radio_port` == 标定口 | 直接拒绝。数传出口 `SerialBridge` 会一直重连同一个口，租约期间它被 `stop_serial_bridge()` 停掉了，但**数据面恢复后又会抢回去**，标定结果会被打断。提示用户先在配置页把数传口改掉或关掉数传 |
| `serial_port` == 标定口 | 允许。这正是"给当前数据源模块标定"的主场景；恢复后数据面继续读这个口，读到的是 RTCM（模块已切基准站），一切自洽 |
| 配置页"扫描串口" | 标定期间**禁用**（前端灰掉）。`/api/serial_ports` 只调 `list_ports.comports()`，不 open，理论上无害；但 `detect_serial()` 里的 `test_serial()` 会 open 并读 2 秒，那会直接抢数据。租约期间 `run_once` 不跑，所以不会触发；仍然在前端禁用，避免用户误以为可以改 |
| 两个标签页同时点"开始标定" | 服务端单实例锁拦截，第二个返回 409（`已有标定任务在进行`） |

## 4. 核心机制二：命令通道

### 4.1 组帧

`$` + 命令体 + `*` + 2 位大写十六进制 XOR + `\r\n`。
XOR 范围是 `$` 与 `*` 之间的全部字符（不含 `$` 和 `*`）。示例：
`PQTMSAVEPAR` → `5A` → `$PQTMSAVEPAR*5A\r\n`。

**发送前必须自检**：如果算出的校验和与驱动里记录的常量不一致，直接判 `BUG` 并中止任务
（而不是发出去）。理由：命令错一个字符，模块会回 `ERROR` 或直接静默，现场极难判断是
"模块不认"还是"我们写错了"。

### 4.1.1 打开串口时的参数（三个默认值都要显式写）

| 参数 | 取值 | 不写会怎样 |
| --- | --- | --- |
| `rtscts` | **False**（显式关硬件流控） | 部分模块默认开 RTS/CTS，而 USB 转串口常不接这两根线 → **能一直收到模块数据，但发命令永远无应答**，看起来像"模块不认命令" |
| `dsrdtr` / `xonxoff` | False | 同上，软件流控偶发吞掉 `$` 起始字节 |
| `timeout` | 0.2 s（读轮询粒度） | 默认 None 会永久阻塞，导致用户点"终止"后线程卡在 read 里、租约迟迟不归还 |
| `write_timeout` | 0.5 s | 不设则模块不收数据时 `write()` 永久阻塞，整个标定线程挂死 |

现有数据源用的是 `serial.Serial(port, baud, timeout=1)`（`serial_source.py`），
没显式关流控——在多数模块上没问题，但标定模块必须显式写死，因为它要**主动发命令**，
而数据源只**被动收数据**。这就是同一份串口参数在两条链路上要求不同的原因。

识别阶段若"收到数据但命令无应答"，第一顺位的排查项就是流控，提示文案要把这条带上。

### 4.2 应答匹配（这是标定能不能稳的关键）

串口上同时存在 4 类字节，必须分开处理：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 目标应答 | `$PQTMVERNO,LG290P03AANR01A03S,...*xx` | 匹配命令名 → 解析 → 结束本次等待 |
| 错误应答 | `$PQTMCFGSVIN,ERROR,1*xx` | 匹配命令名 → 记录错误码 → 立即失败（不重试无意义的重试） |
| 回显 | 模块原样回显我们发的整行 | 丢弃（判定：以我们刚发的命令体开头且不含 `,OK`） |
| 无关输出 | `$GNGGA,...`、`$PQTMSVINSTATUS,...`、RTCM 二进制 `0xD3` | 分别喂给 GGA 缓存 / SVIN 状态缓存 / RTCM 帧缓存，**不算应答** |

**匹配规则要"认前缀不认整行"**：LG290P 的 `PQTMSVINSTATUS` 是**主动输出**的（我们没发命令），
如果把"任何 `$PQTM` 开头"都当应答，会永久错位。所以只匹配"当前正在等的那个命令名"。

### 4.3 超时与重试策略

| 命令类别 | 首等 | 重试 | 重试间隔 | 说明 |
| --- | --- | --- | --- | --- |
| 识别类（VERNO/SN/UNIQID） | 2.0s | 3 次 | 300ms | 模块刚上电可能还在启动，给宽一点 |
| 查询类（`*,R`） | 1.5s | 3 次 | 200ms | |
| 配置类（`*,W`） | 1.5s | 2 次 | 200ms | 配置命令重发是安全的（幂等） |
| `SAVEPAR` | 2.0s | 2 次 | 500ms | 写 NVM 慢，ARM 上偶发 1 秒以上 |
| `SRR`（重启） | **不等应答** | — | — | 文档未定义 `OK` 应答，等它会永久卡住（见 §8.5） |

**重试的边界**：`ERROR` 应答**不重试**（模块明确拒绝，重试只会得到同样的拒绝）；
只有"超时/无应答"才重试。这条区分能省掉大量无意义的 3 次 × 2 秒等待。

### 4.4 混合流：标定期间也会收到 RTCM

CORS 注入成功后，模块会同时收到"我们注入的 RTCM"和"模块自己输出的 NMEA"。
标定的读循环必须能处理**任意切分**的字节流：

- 遇到 `$` → 按行读到 `\n`（单行上限 256 字节，超长判为噪声并重新同步）；
- 遇到 `0xD3` → 按 RTCM 长度字段读整帧 + CRC24Q 校验（复用 `rtcm_parser.crc24q`）；
- 其他字节 → 丢弃并计数（连续 1KB 全是垃圾 → 提示"波特率可能不匹配"）。

### 4.5 错误码文案映射

LG290P 的 `ERROR,<code>`：1=参数错误，2=执行失败，3=该命令不支持。
映射到用户可读文案，并**在界面上直接给出下一步建议**：

| 码 | 文案 | 建议动作 |
| --- | --- | --- |
| 1 | 模块认为参数不合法 | 检查端口/波特率/型号选择是否与实际模块一致 |
| 2 | 模块执行失败 | 重试一次；仍失败则记录并建议重启模块 |
| 3 | 该型号不支持此命令 | **直接切换能力集**，不要重试（典型：LG291P(00) 不支持 `PQTMCFGRTK`；LG290P 不支持 `PQTMCFGANTDELTA`） |

LC29HBS 只返回 1/2，没有 3 —— 这个差异必须在驱动层吃掉，流程层不应感知。

## 5. 核心机制三：驱动抽象

### 5.1 基类能力清单（接口约定，非代码）

| 能力 | 语义 | 谁必须实现 |

由契约测试锁死（§15.1）。

### 5.1.1 命令必须"外置成数据"，不能散在代码里

口述里明确要求："不同厂家、不同型号的模块，重启、固定这些流程和命令都不一样，
需要把这些命令单独提取出来放一个文件，程序运行时提取这个命令来运行。"

落地方式：**每个型号一个驱动文件，文件内的命令集中成一张表**，流程只按"语义键"取命令。

```
rtkserver/calibration/
├── __init__.py
├── service.py            # 状态机 / 任务编排（零命令字符串）
├── lease.py              # 串口租约
├── channel.py            # 组帧、应答匹配、超时重试（零型号知识）
├── geo.py                # GGA→ECEF、3σ、卡尔曼、1005 解码
├── cors.py               # NTRIP 客户端 + GGA 上报
├── store.py              # calibration.db 读写
└── drivers/
    ├── base.py           # 抽象基类 + 能力标记
    ├── quectel_lg290p.py # 命令表 + 解析 + 能力声明
    ├── quectel_lc29hbs.py
    └── generic_observe.py# 未知模块：只观测，不写
```

驱动里的命令表长这样（示意，**不是最终代码**）：

```
CMD = {
  'identify':  'PQTMVERNO',
  'serial_no': 'PQTMSN',
  'uniq_id':   'PQTMUNIQID',
  'get_mode':  'PQTMCFGRCVRMODE,R',
  'set_rover': 'PQTMCFGRCVRMODE,W,1',
  'set_base':  'PQTMCFGRCVRMODE,W,2',
  'set_ecef':  'PQTMCFGSVIN,W,2,0,0,{x:.4f},{y:.4f},{z:.4f}',
  'get_svin':  'PQTMCFGSVIN,R',
  'svin_cfg':  'PQTMCFGSVIN,W,1,{cnt},{acc},0,0,0',
  'msg_rate':  'PQTMCFGMSGRATE,W,{msg},{rate}',
  'save':      'PQTMSAVEPAR',
  'reboot':    'PQTMSRR',
}
CAPS = {'dual_mode': True, 'survey_in': True, 'antenna_info': True, 'antenna_delta': False}
```

**为什么不放 JSON/YAML**：放配置文件的好处是"改命令不用改代码"，但代价是引入运行期
解析错误、校验和无法在编译期核对、以及升级时配置文件与代码版本可能错位的风险。
折中方案是**纯 Python 常量表**：改一行就生效、但仍受代码审查与测试保护；
同时提供 `--dump-driver <model>` 之类的小工具（P5 可选）把表打印给用户对照排查。

**校验和是算出来的，不是抄来的**：表里只存命令体，`*XX` 在发帧时按 XOR 计算，
并且**首次下发某条命令时与文档记录的期望值比对一次**（不一致即判 BUG 中止）。
理由：抄写校验和是这类项目最常见的低级错误来源，而算出来再比对既能防抄错，
又能早发现"参数拼错导致命令体变了"。

**新增型号的成本**：一个文件 + 一张表 + 一个 `parse_line`，不改 `service.py`。
这是"不同厂家命令不一样"这个需求唯一可维护的解法。

### 5.1.2 能力标记驱动 UI，而不是 UI 猜型号

驱动暴露 `CAPS`，前端据此灰化选项（例如 `dual_mode=False` → CORS 标定不可选）。
好处：将来新增一个只有半套命令的国产模块，只要声明能力，UI 自动正确，不用改模板。
服务端在下发配置时**再校验一次**（不信任前端），拒绝不支持的组合并返回明确原因。

### 5.2 识别流程

1. 打开串口后先**静默 300ms**（丢掉上电/插拔瞬间的残帧）；
2. 发 `$PQTMVERNO*58`，把 `VerStr` 拿去做型号匹配（例如 `LG290P03AANR01A03S`）；
3. 匹配到 → 实例化对应驱动 → 读 `PQTMSN*05` / `PQTMUNIQID*16` / `PQTMCFGRCVRMODE,R*32`；
4. 匹配不到但**有数据** → 判定为"未知模块"，走 §5.4 的只观测驱动；
5. 完全没数据 → 逐档波特率重试（顺序：用户所选 → 115200 → 460800 → 921600 → 其他），
   每档 800ms；全部失败 → `串口无有效数据，请检查波特率和模块供电`。

**用户手选了型号但识别不符**：不直接失败，弹出「检测到的是 X，你选的是 Y」，
让用户选"按检测结果继续"或"中止"。理由：LG290P/LG580P/LG680P 的固件字符串前缀不同，
用户很容易选错系列；直接拒绝会让人以为设备坏了。

### 5.3 型号能力矩阵（决定流程分支）

| 能力 | LG290P 系列 | LC29HBS 系列 | 未知 |
| --- | --- | --- | --- |
| 模式切换（流动站↔基准站） | ✅ `PQTMCFGRCVRMODE` | ❌ 无此命令（天生基准站） | ❓ 靠数据类型推断 |
| 固定坐标写入 | ✅ `PQTMCFGSVIN,W,2` | ✅ | ❌ 无命令 |
| Survey-in 自收敛 | ✅ | ✅（少 `<Distance>` 参数） | ❌ |
| CORS 差分标定 | ✅（需切流动站） | ❌（不能跑流动站） | ⚠️ 仅当观测到 NMEA |
| 1033 天线信息 | ✅ `PQTMCFGANTINF` | ❌ | ❌ |
| 1006 天线高 | ❌ 不支持 `PQTMCFGANTDELTA` | ❌ | ❌ |
| 错误码 3（不支持） | ✅ 有 | ❌ 只有 1/2 | — |

> 这张表直接决定 UI 上哪些选项要灰掉：选了 LC29HBS，"CORS 标定"单选就禁用，
> 只剩"写历史坐标"和"Survey-in"两条路。

### 5.4 未知模块：只观测驱动

不发任何命令，只做三件事：

1. 静默监听 **5 秒**（用户需求里给的就是 5 秒）；
2. 统计这 5 秒内的字节构成：NMEA 行数 / RTCM 帧数 / 无法识别的字节数；
3. 判定：

| 观测结果 | 判定 | 后续 |
| --- | --- | --- |
| ≥10 条合法 NMEA，无 RTCM | 流动站 / 普通定位 | 进 CORS 标定线；无 GGA 则启软件生成 |
| ≥3 个合法 RTCM 帧（CRC 通过） | 基准站模式 | **不能标定**（它不输出自身观测的差分，也就没有单点解）→ 提示换模块或直接写历史坐标 |
| 两者都有 | 混合输出（少见） | 以 GGA 是否存在为准：有 GGA 就走 CORS；无 GGA 时按"基准站"处理并提示 |
| 全是噪声 | 波特率不符 / 不是 GNSS | 提示检查波特率与供电 |

## 6. 核心机制四：CORS 链路

### 6.1 建连与错误分类

复用 `sources/ntrip.py` 的 `connect_to_host()`（已带 keepalive 与 `trust_env` 无关的裸 socket），
但**不复用** `handshake_ntrip_client()`（它读的是 `cfg['relay_*']`，语义不同）。

错误必须分类，因为处理动作完全不同：

| 现象 | 判定 | 用户文案 | 是否重试 |
| --- | --- | --- | --- |
| `getaddrinfo` 失败 | DNS / 地址错 | 域名解析失败，请检查服务器地址 | 否 |
| connect 超时 / refused | 网络不通 / 端口错 | 无法连接 `host:port`，请检查网络与端口 | 是（3 次，1/2/4 秒退避） |
| 收到 `401` | 账号密码错 | 用户名或密码错误 | **否**（重试也是错） |
| 收到 `404` | 挂载点不存在 | 挂载点不存在，请重新「读取挂载点」 | 否 |
| 收到 `SOURCETABLE` | 请求到了列表接口 | 该地址返回的是源列表，请确认端口（通常取流与列表同端口，但部分服务不同） | 否 |
| 200 后 5 秒内无数据 | 可能需要 GGA 才给数据 | 已连接但无差分数据（VRS 通常需要先收到 GGA） | 保持连接，先发 GGA 再等 |

**"200 后无数据"这一条是 VRS 的核心坑**：千寻/CORS 类服务在你上报有效 GGA 之前
不会下发任何 RTCM。所以**不能**把"200 后 5 秒无数据"判为失败，而是进入"先发 GGA、
再等数据"的状态。

### 6.2 GGA 策略（本方案里最容易被做错的一环）

| 场景 | 策略 |
| --- | --- |
| 模块原生输出 GGA 且质量 ≥1 | **透传**：从模块读到的 GGA 行原样转发（保持原始精度与质量位），1Hz |
| 模块原生输出 GGA 但质量 =0（未定位） | 仍然转发（质量位 0）。VRS 会拒绝出差分，但**连接不会断**；同时提示"模块尚未定位" |
| 模块不输出 GGA，但有 RMC/GLL/GNS | **软件生成**：从这些语句提取 UTC/lat/lon/alt，按 NMEA 0183 组装 GGA，质量位取 1（单点），卫星数/HDOP 缺失时填 0（未知），差分龄期与站号留空 |
| 模块什么都不输出 | 不可能走 CORS（没有位置），直接判失败并提示检查天线 |

**发送节奏**：严格 1Hz。两条规则：
1. 距上次发送 ≥ 1.0 秒**且**已有新位置才发；
2. 断线重连后**不补发**积压的 GGA（补发会让 VRS 以为你在跳跃）。

**软件生成 GGA 的合规细节**（这几个细节决定 VRS 认不认）：

| 项 | 取值 | 原因 |
| --- | --- | --- |
| Talker ID | 统一 `GN`（`$GNGGA`） | 多系统通用；部分国产模块用 `$GPGGA` 也行，但混用会让日志难以统计 |
| 定位质量 | `1`（单点）；完全未定位时 `0` | 不能填 4（伪固定）。填 4 会让 VRS 误以为你已固定，反而给出错误差分 |
| 卫星数 / HDOP | 能从 GSA/GSV 取到就填真值；取不到**留空** | 留空是合法的（NMEA 允许空字段）。填 `99`/`0` 会被判为无效字段 |
| 海拔 / 大地水准面差距 | 取自 RMC/GLL 的高程；`Sep` 取不到时见 §7.1 的兜底 | 少一个字段会导致 ECEF 高差几米 |
| 差分龄期 / 站号 | 留空 | 单点解本来就没有差分 |
| 校验和 | 按 NMEA 标准 XOR 现算 | 写死会因纬度位数变化而失效 |

**只有 1 Hz 一次 GGA 是不够的吗？** 对 VRS 来说 GGA 就是"申请单"：它告诉服务器
"我在这个位置附近作业，请给我一个该位置的虚拟基准站"。所以：
- 位置跳变会让服务器**换一个虚拟站**，导致 RTCM 参考坐标突变、你的滤波样本被污染——
  这就是 §7.3 要按 3σ 剔除、且断连后必须清空"连续固定解"计数的原因；
- 模块静止时 GGA 坐标只在小范围抖动，属于正常；但如果 1 秒内跳变 > 5 m，说明定位在
  单点/浮动之间来回切，此时**不能开始采集**。

**精度提示**：软件生成的 GGA 只有单点精度，VRS 据此生成的虚拟基准站会带有几米的偏差。
所以软件生成路线必须**在界面上明确标注**"当前为软件生成 GGA，最终精度受单点定位限制（约 1–3 米）"，
不能让用户以为拿到了厘米级。

### 6.3 全双工：单线程超时轮询

```
loop:
    sock.settimeout(0.2)
    try: data = sock.recv(4096)      # 收 RTCM
    except timeout: data = b''
    注入 data 到模块串口（非阻塞写，超时 0.5s）
    if now - last_gga >= 1.0: 取最新位置 → 组 GGA → sendall
    检查累计断连时长 / 用户取消 / 全局超时
```

**为什么不用两条线程**：两条线程共享 socket 时，`sendall` 与 `recv` 虽可并发，但错误处理
（谁负责关闭 fd、谁负责重连）会变成竞态。单线程 0.2 秒轮询的代价是 GGA 最多晚 200ms 发出，
对 1Hz 的 VRS 完全无感。

### 6.4 RTCM 注入

| 要点 | 做法 | 原因 |
| --- | --- | --- |
| 写超时 | 0.5 秒 | 模块串口写阻塞说明它不收了（流控/波特率错），不能无限等 |
| 写失败 | 立即判 CORS 链路失败，转重连 | 半死连接比断开更糟 |
| **绝不 `distribute()`** | 注入的数据只进串口，不进全局分发 | 此刻数据面已停；就算没停，把 CORS 的差分当自身数据转发出去会让下游"用别人的基准站坐标算自己的位置" |
| 缓冲 | 不做队列，直接写 | 上游 1Hz，模块消费能力远大于此；加队列只会引入延迟 |

### 6.5 断连与恢复

- 单次断连：3 次退避（1/2/4 秒）重连，重连成功则继续（**已采集的样本不丢**，
  但会清空"连续固定解"计数，因为断连后可能换了一个虚拟站）；
- 累计断连（含重连失败）> **5 分钟** → 终止任务，判失败（用户需求里的阈值）；
- 每次重连都重新发一次 GGA（不等 1 秒），让 VRS 尽快认出位置。

## 7. 核心机制五：坐标解算

### 7.1 GGA → ECEF

`GGA` 给的是 `lat/lon/alt(MSL) + 大地水准面差距`。ECEF 需要**椭球高**：

```
h_ellipsoid = alt_MSL + geoid_separation
```

然后按 WGS84 标准公式转 ECEF（`a=6378137.0`，`f=1/298.257223563`）。
**注意**：现有 `utils/common.py` 只有 `ecef_to_latlon`（反算），标定要新增正向函数，
并且**必须做往返自检**（已知点 → ECEF → 反算 → 偏差 < 1e-6°，用测试锁死）。
这个自检能挡住"经纬度顺序写反""度分秒与十进制度混用"这类致命错误。

**`Sep`（大地水准面差距）缺失怎么办**：这是必须写的兜底，否则高程会错几米，
而高程误差在 ECEF 上会串到 X/Y/Z 三个分量，1005 校验必然超差。

| 情况 | 处理 | 界面 |
| --- | --- | --- |
| `Sep` 有值 | 直接用 `h = alt + Sep` | 无提示 |
| `Sep` 为空、模块是已知型号 | 用该型号**最近一次拿到的 Sep**（同一场地变化很小，厘米级） | 标注"高程使用缓存的大地水准面差距" |
| `Sep` 为空、无缓存 | 用**按纬度线性插值**的粗估值（中国大陆约 −10 ~ −40 m；写成一个可改的常量表，不引入 EGM96 大文件） | 黄色提示"高程精度降低（约 ±2 m），平面精度不受影响" |
| `Sep` 为空且用户要求高精度 | 该项标定**仅用于平面**，高程在记录里标 `height_quality=low` | 明确告知 |

**为什么不用 EGM96 全量模型**：几十 MB 的网格文件对一个跑在 1 GB 内存 ARM 盒子上的
服务端来说不划算，而标定的目的是"基准站坐标"，平面（X/Y）是主要矛盾；高程用缓存+粗估
已经够用，且这个误差不会随时间漂移（同一地点是系统偏差，可事后修正）。
如果将来真的需要厘米级高程，再加一个可选的小范围 geoid 文件即可，接口不用变。

### 7.2 固定解准入

连续 **30 秒**同时满足：

| 条件 | 阈值 | 数据来源 | 依据 |
| --- | --- | --- | --- |
| GGA 质量位 | `=4`（RTK 固定解） | **GGA** 第 6 字段 | NMEA 定义；3=浮点解不可用 |
| 卫星数 | `≥12` | **GGA** 第 7 字段（无效时取 GSV 计数） | 用户需求；低于 12 时高程收敛很慢 |
| PDOP | `≤2.0` | **GSA** 的 PDOP 字段 | 几何构型；PDOP>3 时高程误差会被放大 3 倍以上 |

**PDOP 只能从 GSA 拿，不能从 GGA 拿**——GGA 里只有 HDOP（水平精度因子），
没有 PDOP（三维）。如果驱动只解析 GGA/RMC/GLL，这条判据实际上永远不会生效，
表现为"条件写得很严，但代码里恒真"，是最典型的"看起来实现了其实没实现"。

因此：

1. 驱动必须解析 `GSA`（`$GxGSA`），取第 15 字段 PDOP；`GSA` 有多个 talker（GP/GL/GA/GB/GQ），
   **取当前正在用于解算的那一条**（通常与 GGA 的 talker 一致，取不到就取最后一条有效值）；
2. `GSA` 的 `Mode`（第 2 字段）必须为 `3`（3D 定位），`2`（2D）时 PDOP 不可用；
3. 模块若完全不输出 `GSA`（部分固件可关），降级为 **HDOP ≤ 1.5** 并在界面上注明
   "仅校验水平精度"——不能悄悄把条件从 PDOP 换成 HDOP，否则用户以为在严格校验。

任一条不满足 → 计数器归零重来。**为什么要 30 秒**：刚进固定解的头几秒，接收机内部
模糊度刚固定，坐标还会跳几厘米；30 秒能滤掉"瞬时假固定"。

### 7.3 3σ 野值剔除

- 滑动窗口 N=30（1Hz 下 = 30 秒）；
- 逐轴算 μ 与 σ，剔除 `|x-μ| > 3σ` 的点；
- **边界情况**：σ 极小时（例如全静止，σ≈0.0001），3σ 会把正常的 1cm 抖动全部剔掉，
  导致样本数不增长。处理：σ 下限钳到 0.005 米（5mm），低于此按 5mm 算。
- 剔除比例 > 30% → 判"多路径严重/环境不稳"，界面警告但继续。

### 7.4 一维卡尔曼（纯 Python，无 numpy）

常值模型（状态只有位置，没有速度）：

```
预测： x = x            P = P + Q
更新： K = P / (P + R)
       x = x + K*(z - x)
       P = (1-K)*P
```

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 初值 x0 | 前 10 个有效样本的均值 | 避免从 0 开始收敛要很久 |
| P0 | 1.0 m² | 表示"完全不确定" |
| Q（过程噪声） | 1e-6 m²/s | 天线不动，位置理论上常量；Q 只是允许缓慢漂移 |
| R（观测噪声） | 0.0004 m²（σ=2cm） | GGA 无精度字段时的保守值；有 `quality` 时可粗调 |

三轴独立滤波（E/N/U 分开），因为它们的噪声特性差异很大（高程通常差 2–3 倍）。

### 7.5 收敛判定与输出

**双终止条件（满足其一）**：

1. 达到用户设定的时长（3 / 5 / 10 分钟可选，默认 5 分钟）；
2. 连续 **60 秒**三轴滤波后标准差均 ≤ **0.02 米**。

输出：

| 字段 | 来源 |
| --- | --- |
| ECEF X/Y/Z | 三轴滤波终值的均值，保留 4 位小数（与 `PQTMCFGSVIN` 的精度一致） |
| accuracy | 三轴 σ 的合成：`sqrt(σx²+σy²+σz²)` |
| 样本数 / 剔除数 / 实际时长 | 统计 |
| 经纬高 | 反算，供页面显示 |

### 7.6 不收敛怎么办

达到最大时长（30 分钟）仍不满足条件：

- **不自动失败**：把当前结果连同"未达目标精度"标记一起展示；
- 给三个选项：① 采用当前结果并继续写入；② 延长 10 分钟；③ 终止；
- 采用不达标结果时，写入的 `accuracy` 字段如实记录（后续排查"为什么我的基准站差 10cm"时，
  这个字段是唯一线索）。

## 8. 核心机制六：写入 → 保存 → 重启 → 校验

### 8.1 顺序与依据

| 步 | 命令 | 回读校验 | 超时 | 失败动作 |
| --- | --- | --- | --- | --- |
| 1 | `$PQTMCFGSVIN,W,2,0,0,<X>,<Y>,<Z>*xx` | `$PQTMCFGSVIN,R` → 模式=2 且三轴偏差 ≤ 0.001m | 3s | 重试 1 次（重发同一坐标是幂等的）；仍失败 → 中止，模块保持流动站模式 |
| 2 | `$PQTMCFGRCVRMODE,W,2*29` | `$PQTMCFGRCVRMODE,R` → 2 | 2s | 重试 1 次；仍失败 → 中止 |
| 3 | `$PQTMCFGMSGRATE,W,RTCM3-1005,1*59`（+1033/107X…） | `$PQTMCFGMSGRATE,R,RTCM3-1005` → 1 | 2s | 单条失败只记警告（缺 1005 会导致最终校验做不了，所以 1005 失败要中止；1033 失败可继续） |
| 4 | `$PQTMSAVEPAR*5A` | 收到 `,OK` | 2s | 重试 2 次；仍失败 → 中止（不重启，避免重启后配置丢失） |
| 5 | `$PQTMSRR*4B` | **不等应答**，等 `$PQTMVER` 首帧 | 8s | 见 §8.5 |
| 6 | 重启后 `$PQTMCFGRCVRMODE,R` / `$PQTMCFGSVIN,R` | 模式=2、坐标一致 | 3s | 失败 → 判"配置未持久化"，提示检查模块 NVM |
| 7 | 监听 RTCM，解 1005 | `|Δ| ≤ 0.05m` | 10s | 超差 → 警告（不判失败），见 §8.6 |

**为什么先写坐标再切模式**：`PQTMCFGSVIN` 在流动站模式下也能写（只是不生效）；
反过来先切基准站，模块会立刻停止输出 NMEA，此时若 `CFGSVIN` 写入失败，模块就停在
"基准站 + 坐标=0,0,0" 这个最糟糕的状态。先写坐标能把风险窗口压到最小。

### 8.1.1 写进去的必须是 ARP，不是 APC（方向极易搞反）

`PQTMCFGSVIN` 写的是**天线参考点（ARP）**的坐标，而仪器对中、测量得到的通常是
**相位中心（APC）**。两者差一个天线偏移量：

```
ECEF(ARP) = ECEF(APC) − Δ_ant        （Δ_ant 为 APC 相对 ARP 的偏移，在 ECEF 各轴上分解）
```

**符号为什么是减**：APC 在天线参考点之上（沿站心天顶方向 U 为正）。测得的是 APC，
要写进模块的是 ARP，所以要把向上那一截**减掉**。写成加号会让基准站整体抬高
"两倍天线高"，下游所有流动站的高程一起错。

方向的正负号无法靠代码自动判断（用户填的可能是 NED，也可能是 ENU），所以：

| 做法 | 说明 |
| --- | --- |
| 默认偏移全 0 | 99% 的场景天线是"ARP 就在对中点"的机型，或用户不在意这几厘米 |
| 开放填写时**只接受 ENU** | UI 上三格标 `E/N/U`，并在旁边写"U 为相位中心相对 ARP 的高度，通常为正" |
| 填写后必须**回显换算结果** | 显示"测量 APC = …，扣除偏移后写入 ARP = …"，让用户能核对 |
| 记录里存两套值 | `apc_*` 与 `ecef_*`（实际写入值），事后能反推当时填了什么 |

**1006/1033 的天线高是另一回事**：RTCM 1006 的 DF028 是"天线高"，由流动站读取后自己扣除。
LG290P 不支持 `PQTMCFGANTDELTA`，所以这个字段在 LG290P 上**写不进去**——这意味着
即使我们对 ARP 做了精确扣除，流动站侧也拿不到天线高信息。取舍：**统一按 ARP 写坐标**，
并在使用端（流动站）配置天线高，而不是假装能通过 1006 传递。

### 8.2 回读阈值 0.001m 的依据

`PQTMCFGSVIN` 的 ECEF 参数是 4 位小数（0.1mm 分辨率）。理论上回读应当**完全一致**。
取 1mm 是为了容纳模块内部的 float→int 舍入（部分固件会做 cm 级量化）。
**如果回读偏差是整米级**，那不是舍入，是"根本没写进去"或"读错了字段"，必须判失败。

### 8.3 切模式后 NMEA 关闭 → 应答不确定性的降级判定

文档明确：切到基准站模式后模块**自动关闭 NMEA 输出**。而 `PQTM` 的 `,OK` 应答是否
仍输出，文档没有明确保证。

因此第 2 步的校验采用**两段式**：

1. 切模式后 1.5 秒内收到 `$PQTMCFGRCVRMODE,OK,2` → 直接通过；
2. 没收到 → **不判失败**，而是继续走完保存+重启，在重启后（模块一定重新输出
   `$PQTMVER`，且此刻已处于基准站模式）再读 `CFGRCVRMODE,R` 做最终确认。

这条降级路径是必须的，否则在"基站模式不输出 NMEA 应答"的固件上，标定会 100% 失败，
而实际上是成功的。

### 8.4 保存的关键点

- `SAVEPAR` 是**全局保存**：它把当前内存里所有配置一次写进 NVM。
  所以必须**在所有配置命令之后**、**重启之前**执行一次，不要中间多存。
- 如果 `SAVEPAR` 失败，**绝不能重启**：重启会让未保存的配置回到旧值，
  用户会看到"标定成功了但坐标还是老的"。
- 保存后立刻读一次 `CFGSVIN,R` 作为"内存态确认"，重启后再读一次作为"NVM 态确认"。
  两次都过才算真的写进去了。这条是用户明确要求的"保存过后检查一遍，核对一遍"。

**保存失败必须回写内存态（否则会留下一个"看不见的不一致"）**：

`SAVEPAR` 失败时，模块的**内存**里已经是新坐标、新模式，而 **NVM** 里还是旧值。
这时如果因为别的原因（看门狗复位、用户拔电、下次上电）模块重启，配置会静默回到旧值。
用户看到的现象是"标定明明成功了，用了几天坐标自己变回去了"，几乎无法归因。

所以失败路径必须做三件事，按顺序：

| 步 | 动作 | 失败后果 |
| --- | --- | --- |
| 1 | 用**备份的旧值**回写：`CFGSVIN,W,2,<旧X>,<旧Y>,<旧Z>` + `CFGRCVRMODE,W,<旧模式>` | 回写也失败 → 标记 `nvm_state=unknown` |
| 2 | 再读一次回读，确认内存态已回到旧值 | 不一致 → 同上 |
| 3 | 界面文案必须区分三种情况 | 见下表 |

| 最终状态 | 界面文案 | 记录字段 |
| --- | --- | --- |
| 回写成功 | "配置保存失败，已恢复为标定前的配置（当前是临时状态，请重试标定）" | `nvm_state=reverted` |
| 回写失败 | "配置保存失败且未能恢复。**断电重启后模块会回到标定前的配置**，请重新标定" | `nvm_state=unknown` |
| 保存成功 | 正常继续重启流程 | `nvm_state=saved` |

`nvm_state` 要落进 `calibration_records`，因为"这条记录到底有没有真的写进模块"
是事后排查最需要的信息——没有这个字段，用户报"坐标变了"时只能靠猜。

### 8.5 重启完成判定

`PQTMSRR` 文档**没有 `OK` 应答**（对比 `SAVEPAR` 有）。所以：

```
发 SRR → 关闭串口 → 等 800ms → 重开串口 → 等 $PQTMVER（最多 8 秒）
```

- 收到 `$PQTMVER` → 判定重启完成（文档写明"每次成功启动后均会先输出该语句"）；
- 8 秒内没收到但串口有数据 → 也认为重启完成（部分固件首帧不是 VER）；
- 8 秒内串口完全静默 → 判"模块未重启"，提示"请断电重启模块后重新校验"。

**关掉串口再重开**是必要的：某些 USB 转串口在模块复位时会重新枚举（`/dev/ttyUSB0` 变成
`/dev/ttyUSB1`），不重开就会读到一个已经失效的 fd。重开时按 §5.2 的"枚举 + 匹配"逻辑
重新找口，而不是死认原来的设备名。

### 8.6 1005 最终校验

解析 RTCM3-1005：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| DF003 | 基准站 ID | 可写入用户指定值（默认 0） |
| DF025/026/027 | ECEF X/Y/Z | **核心**：与本机写入值比对 |

- 1005 的 ECEF 以 0.1mm 为单位编码，量化误差 ≤ 0.1mm，所以 0.05m 的阈值**远大于**量化误差，
  是"真超差"而不是"编码精度不够"。
- 偏差 0.05–0.5m → 警告 + 展示具体差值，允许用户确认后继续（可能是模块内部做了平滑）；
- 偏差 > 0.5m → 判失败，提示"模块报告的基准站坐标与写入值不符，可能是写入未生效或读到了旧配置"。

**这条校验验证什么、不验证什么**（极易被误读，务必分清）：

- **验证的是**："写入 → NVM 保存 → 重启 → 编码播发"整条链路确实生效，下游移动站拿到的是新坐标。
  相对于"读 `PQTMCFGSVIN` 回读配置"，它多覆盖了 NVM 持久化与播发编码两段，所以仍然必要。
- **不验证的是**：坐标的**绝对精度**。1005 播发的是模块内部存的那份值，与写入值同源；
  写入成功时偏差恒等于 1005 的量化误差（≤0.1 mm）。把 0.1 mm 当成"坐标精度 0.1 mm"是
  **循环验证**——它连 1 米的天线高错误都发现不了（写错多少就播错多少）。
  绝对精度只能靠**独立观测**：交叉解算复测、换基准源比对、已知控制点比对、静态 PPP 后处理。

### 8.7 1033 注入与能力限制

- LG290P：`$PQTMCFGANTINF,W,<AntDsc>,<AntSetupID>,<AntSN>*xx`
  - 天线描述：`2RTK-<型号>`，长度受 RTCM 1033 的 DF030 限制（建议 ≤ 16 字符）
  - AntSetupID：用标定方式编码（1=Survey-in，2=CORS，3=历史坐标），便于事后从 1033 反查
  - AntSN：模块 SN
- **LG290P 不支持 `PQTMCFGANTDELTA`**（原文：仅 LG291P(00) 支持且开发中）→ 1006 的
  DF028 天线高写不进去。这意味着"天线高"只能在使用端手动配置，界面必须说明，不能让用户
  以为写进去了。
- LC29HBS：无天线信息命令 → 跳过，记录"该型号不支持 1033 自定义"。

## 9. 状态机

### 9.1 状态清单

| 状态 | 含义 | 正常出口 | 超时 | 失败回退 |
| --- | --- | --- | --- | --- |
| `IDLE` | 无任务 | 收到 start | — | — |
| `PREPARE` | 校验参数、写租约 | → `HOLD` | 5s | `FAILED`（未动硬件，最安全） |
| `HOLD` | 让位、等串口释放 | → `OPEN` | 8s | `FAILED` + 解除 gate |
| `OPEN` | 打开串口、清缓冲 | → `DETECT` | 3s | `FAILED` |
| `DETECT` | 识别型号/SN/模式 | → `PLAN` / `OBSERVE` | 15s | `FAILED`（"模块无应答"） |
| `OBSERVE` | 未知模块静默观测 5s | → `PLAN` | 8s | `FAILED` |
| `PLAN` | 决定路线，必要时等用户选择 | → 对应分支 | 用户决定（不计时） | `ABORTED` |
| `ROVER_SETUP` | 切流动站→保存→重启→回读 | → `NMEA_SETUP` | 25s | 重试 1 轮 → `FAILED` |
| `NMEA_SETUP` | GGA 1Hz / FIXRATE 1Hz | → `GGA_WAIT` | 10s | 重试 1 次 → `FAILED` |
| `GGA_WAIT` | 等 3 条有效 GGA | → `CORS_CONNECT` | 30s | 无 GGA → 启软件生成；仍无数据 → `FAILED` |
| `CORS_CONNECT` | NTRIP 建连（含 401/404 分类） | → `FIX_WAIT` | 45s（3 次退避） | `FAILED`（带原因） |
| `FIX_WAIT` | 连续 30s 固定解 + 卫星≥12 + PDOP≤2 | → `COLLECT` | 10 分钟 | `FAILED`（"长时间未固定"） |
| `COLLECT` | 采集 + 3σ + 卡尔曼 | → `CORS_CLOSE` | 30 分钟 | 超时未收敛 → 让用户决定 |
| `CORS_CLOSE` | 断开 CORS，停 GGA | → `WRITE_COORD` | 3s | 忽略错误 |
| `WRITE_COORD` | 写固定坐标 + 回读 | → `BASE_SETUP` | 10s | 重试 1 次 → `FAILED` |
| `BASE_SETUP` | 切基准站 + 回读（含降级） | → `MSG_SETUP` | 10s | 重试 1 次 → `FAILED` |
| `MSG_SETUP` | 1005/1033/MSM 配置 | → `SAVE` | 10s | 1005 失败 → `FAILED`；其余仅警告 |
| `SAVE` | `SAVEPAR` + 内存态回读 | → `RESTART` | 6s | 重试 2 次 → `FAILED`（不重启） |
| `RESTART` | `SRR` + 重开串口 + 等 VER | → `VERIFY_MODE` | 12s | `FAILED`（"模块未重启"） |
| `VERIFY_MODE` | 重启后回读模式/坐标 | → `VERIFY_RTCM` | 6s | `FAILED`（"配置未持久化"） |
| `VERIFY_RTCM` | 解 1005 + 30s 稳定性 | → `INJECT` | 45s | 超差 → 警告后仍可 `INJECT` |
| `INJECT` | 1033 / 本地 Caster STR / mDNS | → `DONE` | — | 失败只警告 |
| `DONE` | 成功 | 归还租约 | — | — |
| `FAILED` | 失败（带原因与阶段） | 归还租约 | — | — |
| `ABORTED` | 用户取消 | 归还租约 | — | — |
| `INTERRUPTED` | 断电/进程被杀（启动时判定） | — | — | 只标记，不自动改硬件 |

### 9.2 迁移主干（成功路径）

```
IDLE → PREPARE → HOLD → OPEN → DETECT → PLAN
                                          ├─(历史坐标)──────────────┐
                                          ├─(双模+CORS) ROVER_SETUP → NMEA_SETUP → GGA_WAIT
                                          │              → CORS_CONNECT → FIX_WAIT → COLLECT
                                          │              → CORS_CLOSE ─┤
                                          ├─(Survey-in) BASE_SETUP → … │
                                          └─(未知/RTCM) PLAN 分支      │
                                                                       ▼
                                                        WRITE_COORD → BASE_SETUP → MSG_SETUP
                                                        → SAVE → RESTART → VERIFY_MODE
                                                        → VERIFY_RTCM → INJECT → DONE
```

**任何状态都可以被 `ABORT` 打断**，统一走 `release()`（§3.3）。唯一的例外是
`SAVE` 与 `RESTART` 之间——此时中断会让 NVM 与内存不一致，所以这两个状态**禁止打断**，
取消请求只做标记，等 `RESTART` 完成后立刻进 `ABORTED` 回收。

### 9.3 状态落盘

`.calibration/state.json`（原子写），字段：

```json
{
  "stage": "COLLECT",
  "stage_text": "采集与滤波",
  "progress": 62,
  "message": "已采集 187 点，σ=0.013m",
  "error": "",
  "finished_at": "",
  "started_at": "2026-11-01 12:00:00",
  "mode": "cors"
}
```

**为什么落盘而不是纯内存**：用户会关页面、会换手机看、会在标定 10 分钟后回来看进度。
`maintenance.js` 已经证明了这套"状态文件 + 轮询"的模式可靠（升级就是这么做的）。

### 9.4 单实例约束

`service.start()` 用一把模块级 `threading.Lock` + 状态里的 `stage` 双重判定；
进程内不可能有两个标定任务。跨进程不需要考虑（只有 Web 单进程能发起）。

**明确写死一条**：当前版本**全局只允许一个标定任务**，不区分串口。原因是租约虽然按串口维度
设计（`lease.json` 里带 port），但"数据面让位"是全局的——`restart_event` 一置位，
所有出口和数据源都会停，第二个任务即使占了另一个口也没有数据面可让。

将来若要多串口并行，改动点是"让位"的粒度：把 `run_once` 的停止范围从"全部"缩到"某一源"，
而不是改租约。现在不做，但接口按 port 索引留好了位置。

## 10. 五条业务主线（用户场景 → 具体步骤）

### P1 已知双模 + CORS（精度最高，5–15 分钟）

```
识别 → 记录原模式/原配置（备份）→ 切流动站(保存+重启,回读)
→ 配 GGA 1Hz + FIXRATE 1000ms → 等 3 条 GGA（无则软件生成）
→ 连 CORS（分类错误）→ 1Hz 转发 GGA → 等 30s 连续固定解
→ 采集 5 分钟 / σ≤2cm 稳定 60s → 断 CORS
→ 写 CFGSVIN,W,2 + 回读 → 切基准站 + 回读 → 配 1005/1033/MSM
→ SAVEPAR（+内存态回读）→ SRR（+重开串口+等 VER）→ 回读模式/坐标
→ 解 1005 比对 → 注入 1033/STR/mDNS → 恢复数据面
```

### P2 已知双模 + 历史坐标（20–40 秒，风险最低）

```
识别 → 读历史记录（同 SN 优先，其次同位置）→ 确认坐标
→ 写 CFGSVIN,W,2（可选叠加天线偏移）→ 切基准站 → 配报文 → 保存 → 重启 → 1005 校验
```

**这是 P0 阶段要优先实现的最小闭环**，因为它几乎不依赖 CORS、不依赖滤波，
却覆盖了"天线没动过"这个最常见场景。

### P3 Survey-in 自收敛（10–60 分钟，无网可用）

```
识别 → 切基准站(保存+重启,回读) → CFGSVIN,W,1,<次数>,<精度>,0,0,0,[<距离>]
→ 开 PQTMSVINSTATUS 1Hz → 轮询直到 Valid=2 且 Obs≥设定 且 MeanAcc≤阈值
→ SAVEPAR → SRR → 1005 校验（阈值放宽到 0.1m）
```

**三档参数（注意与官方默认值的差异）**：

| 档位 | 观测次数 | 3D 精度阈值 | 预计耗时 | 说明 |
| --- | --- | --- | --- | --- |
| 快速 | 600 | 3.0 m | ~10 min | 临时建站 |
| 标准 | 1800 | 1.5 m | ~30 min | 常规野外 |
| 高精度 | 3600 | 0.8 m | ~60 min | 长期固定 |

> ⚠️ **`<3D_AccLimit>` 在 LG290P 上的默认值是 0.0，含义是"不限制精度"**，不是"最高精度"。
> LC29HBS 同一字段默认 15.0。跨型号移植时这是最容易翻车的一处，驱动必须显式下发。

### P4 未知模块（自适应，只靠数据类型）

```
静默 5s → 判 NMEA / RTCM / 噪声
├ NMEA 且有 GGA  → 走 CORS 标定（同 P1 的 CORS 段）
├ NMEA 但无 GGA  → 启软件生成 → 走 CORS 标定（精度受限，界面标注）
├ RTCM           → 拒绝标定，提示"该模块运行在基准站模式，无法测天线相位中心"
└ 噪声           → 提示波特率/供电
```

标定完成后若模块仍能识别型号 → 尝试写入；不能识别 → 只保存坐标，提示用户
"坐标已保存，请更换为目标基站模块后写入"。

### P5 外部流动站两段式（LC29HBS 等纯基准站）

这是唯一需要**人工拔插**的流程，也是状态机里唯一有"等用户"状态的流程。

```
段1（流动站）：插入流动站模块 → 识别 → 走 P1 的 CORS 段 → 得到 ECEF → 存库
              ↓ 状态 = WAIT_SWAP，页面显示"请断电，更换为目标基准站模块"
段2（基准站）：用户点"已更换" → 重新枚举/重开串口 → 识别新模块
              → 从库取坐标 → 写坐标 → 切/确认基准站 → 保存 → 重启 → 1005 校验
```

关键设计：

- `WAIT_SWAP` 状态**不计超时**，但落盘 `stage`，所以关页面、重启进程都不丢；
- 用户点"已更换"后才重新 open 串口（旧 fd 已随拔线失效，必须重新枚举）；
- 如果重新识别出**还是原来那块**（SN 相同）→ 提示"检测到的仍是 <SN>，请确认已更换"；
- 如果段 2 失败，坐标已在库里，用户可以随时用 P2 重来，不必重新测。

**状态区**走"时间线 + 指标"两栏：

### 11.2 接口清单

| 方法 | 路径 | 用途 | 备注 |
| --- | --- | --- | --- |
| GET | `/api/calibration/options` | 型号列表、能力矩阵、历史坐标、默认参数 | 一次拉全，减少往返 |

### 11.3 为什么用轮询而不是 `/ws`

`/ws` 是**公开通道**（未登录也能连，只是坐标会被 `_redact_for_public` 打码）。
标定过程包含 CORS 口令、精确 ECEF、模块 SN，这些绝不该进公开广播。
用登录态的 HTTP 轮询 + `cache: no-store` 是唯一安全且简单的选择。

代价是每秒一个请求，在局域网 ARM 板上完全可接受（升级页也是这么做的）。

### 11.4 口令与坐标的显示

- CORS 密码：提交后前端只保留掩码 `******`；后端返回的状态里**永不回显**；
- 日志尾：输出前统一过一遍 `mask_config` 同款规则（含 `password`/`passwd`/`secret` 的字段打码）；
- ECEF：页面上显示到 4 位小数（与写入精度一致），同时给一份经纬高便于人工核对。

### 11.5 页面关闭 / 刷新 / 多标签

| 场景 | 行为 |
| --- | --- |
| 关掉页面 | 任务继续（服务端线程），下次打开接管进度 |
| 刷新 | `status` 返回 `stage` 非终态 → 直接进"运行中"形态，继续轮询 |
| 多标签 | 都轮询同一个状态，任一标签点终止都能生效（服务端幂等） |
| 会话过期 | `status` 返回 401 → 显示"登录已过期，标定仍在进行"并提供重新登录链接 |

### 11.6 交互边界

- 标定运行中：串口/模块/方式/CORS 全部只读；
- 「开始」前必须二次确认，确认框里写明**预计停服时长**与**下游会断流**；
- 若检测到 `local_caster_enabled=1` 且当前有在线客户端 → 确认框追加"当前有 N 个客户端连接，标定期间会断开"。

## 12. 数据模型

### 12.1 为什么独立 `calibration.db`

| 理由 | 说明 |
| --- | --- |
| 语义分离 | `settings` 是"配置"，会被人为重置；标定记录是"资产"，重置配置不该清掉 |
| 故障隔离 | 标定库损坏/写满，绝不能影响配置页与主程序（`get_config()` 已在 0 字节时退回默认值，没必要再叠一层风险） |
| 迁移自由 | 后续加字段、加索引不碰主库 |
| 备份简单 | 用户想备份"我的基准站坐标"，只要拷一个文件 |

位置：`<BASE_DIR>/calibration.db`（与 `2RTKserver.db` 同级），WAL 模式，`timeout=10`。

### 12.1.1 升级 / 卸载 / 重置时必须处理这张库

这是"独立库"带来的**唯一额外成本**：现有 `update.sh`、`uninstall.sh`、`reset_config.py`
都不知道它的存在。三处都要改，否则升级一次就把用户的标定资产弄丢。

| 动作 | 现状 | 必须补 |
| --- | --- | --- |
| **升级**（`runner.py` 的 `backup()` / `apply()`） | 只处理 `rtkserver/` 目录与 `.version`，`calibration.db` 在根目录不会被覆盖（因为复制清单里没有它） | ① 备份时**一并复制** `calibration.db` 到备份目录（含 `-wal`/`-shm`）；② 升级后用 `PRAGMA user_version` 做**表结构版本校验**，旧库缺列则 `ALTER TABLE` 迁移，不重建 |
| **卸载**（`runner.py` 的卸载分支） | 备份 `2RTKserver.db` 到 `/root` | 同目录一并备份 `calibration.db`，且**默认保留**（它是资产）；提示语里明确列出"已备份：标定记录 N 条" |
| **重置配置**（`reset_config.py`） | 只清 `settings` 表 | **绝不动** `calibration.db`。语义上"重置配置"不该删掉测量结果；如果要连标定一起清，必须另给一个显式参数（如 `--purge-calibration`）且二次确认 |

**表结构版本化**：`calibration.db` 里用 `PRAGMA user_version = 1` 记录 schema 版本，
迁移函数写成 `_migrate(conn, from_ver)`，只做增量。这样"2.3 升级到 2.4 时加了
`nvm_state` 字段"不会让老库直接崩在读列上。

**备份文件命名**：与主库一致的时间戳风格，避免两次备份互相覆盖：
`2rtk-calibration-YYYYMMDD-HHMM.db`。

**升级期间的并发**：数据库复制必须在标定任务空闲时做（`state.stage == idle`）。
如果用户正在标定就点升级，`upgrade` 会先停服务，标定线程随之被杀——所以
`calibration` 的启动钩子要把"上次非终态"标记为 `INTERRUPTED`（§14 #20），
不能让 `stage` 永久卡在 `COLLECTING`。

### 12.2 表结构

**`calibration_records`**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | |
| module_sn | TEXT | 模块 SN（未知模块为空） |
| module_model | TEXT | LG290P / LC29HBS / unknown |
| firmware | TEXT | `PQTMVERNO` 的 VerStr |
| method | TEXT | `cors` / `survey_in` / `manual` / `external_rover` |
| ecef_x/y/z | REAL | 米，4 位小数 |
| accuracy | REAL | 3D σ，米 |
| lat/lon/height | REAL | 反算，便于人看与源列表 |
| samples | INTEGER | 有效样本数 |
| duration | INTEGER | 秒 |
| ant_delta_e/n/u | REAL | 天线偏移（用户手填，默认 0） |
| verified | INTEGER | 1005 校验是否通过（0/1/2=警告） |
| verify_delta | REAL | 1005 与写入值的最大轴偏差 |
| created_at | TEXT | 本地时间 |
| remark | TEXT | |

索引：`(module_sn, created_at DESC)`、`(created_at DESC)`。

**`module_profiles`**（型号能力表，便于后续扩型号不改代码）

| 字段 | 说明 |
| --- | --- |
| model_key | `lg290p` / `lc29hbs` |
| display_name | 界面显示名 |
| match_prefix | 固件字符串前缀（如 `LG290P`） |
| caps | JSON：`{"set_mode":true,"svin":true,"ant_info":true,"err3":true}` |

**`calibration_events`**（可选，P2 阶段再加）：每次任务的阶段流水，用于"哪一步最容易失败"的统计。

### 12.3 与 `settings` 的关系

标定**只读** `settings`（拿 `serial_port`/`radio_port`/`local_caster_*` 做冲突判断），
**不写**。唯一例外是用户显式点「设为当前数据源」，那个接口写 `mode=serial` +
`serial_port=<口>` + `baud_rate=<值>`，然后置 `restart_event`。

### 12.4 保留策略

每 SN 保留最近 50 条，超出按时间删最旧；总量上限 5000 条（约 1MB）。
**不自动删"最后一次成功"记录**，因为那是用户的救命坐标。

## 13. 标定完成后的信息上链

| 目标 | 做法 | 是否必须 |
| --- | --- | --- |
| 模块 RTCM 1005 | 由模块自身输出（我们写的坐标） | 必须（就是标定的目的） |
| 模块 RTCM 1033 | `PQTMCFGANTINF`（LG290P）/ 跳过（LC29HBS） | 建议 |
| 本地 Caster 源列表 | 无需改代码：`_build_sourcetable_response()` 读 `state.station_info`，而 1005 解析会自动填它 | 自动生效 |
| 首页地图/坐标 | 同上，`station_info` 自动更新 | 自动生效 |
| mDNS NTRIP 记录 | `_sync_mdns_ntrip_port()` 已处理端口；坐标不在 mDNS 里 | 无需改 |
| 标定记录页 | 写 `calibration.db` | 必须 |

**这里有一个"免费复用"值得强调**：标定只要把正确坐标写进模块，模块播出的 1005 就会让
`rtcm_parser.process_station_message()` 自动更新 `state.station_info`，
于是本地 Caster 的 STR 行、首页地图、下游移动站看到的源信息**全部自动变正确**——
不需要为"信息上链"写任何新代码。

唯一需要新增的是 STR 里的"标定方式/精度"这类描述性字段。若要做，改动点只有
`_build_sourcetable_response()` 的一行字符串拼接，且必须保证长度不超过 NTRIP 的
STR 行限制（建议描述控制在 60 字符内）。

### 13.1 这套"自动生效"有一个前提，必须说清

`station_info` 是 `rtcm_parser.process_station_message()` 解析**当前数据源**的 RTCM 时填的。
所以"标定完地图自动就对"成立的前提是：**被标定的串口就是当前数据源串口**。

如果用户标定的是另一个口（例如设备上插了两块模块，标定的是备用那块），那么：

- 模块本身坐标已经写对了 → 它自己播的 1005 是对的；
- 但 `rtcm_parser` 根本没在读那个口 → `station_info` 不会变 → 首页地图和源列表**还是旧值**。

这不是 bug，但**用户会认为标定失败**。所以收尾必须按"该口是否等于当前数据源"分两种文案：

| 情况 | 完成文案 |
| --- | --- |
| 标定口 == 当前数据源 | "标定完成。基准站已在播发新坐标，地图与源列表已更新。" |
| 标定口 ≠ 当前数据源 | "标定完成，坐标已写入模块。**该串口当前不是数据源**，把它设为数据源后地图与源列表才会更新。"（此时才显示"设为数据源"按钮） |

顺带一条：`state.station_info` 在 `reset_runtime_state()` 里会被清空（换数据源时），
所以切换数据源后的头几秒地图是空的，这是既有行为，不是标定引入的问题。

## 14. 异常矩阵

| # | 异常 | 检测方式 | 处理动作 | 用户可见 | 影响主程序 |
| --- | --- | --- | --- | --- | --- |
| 1 | 串口被拔 / 模块断电 | `read()` 抛 `SerialException` 或连续 3 秒无任何字节 | 立即 `FAILED`，归还租约 | 串口连接中断，请检查模块供电和接线 | 否（数据面恢复后自行重扫） |
| 2 | 模块完全无应答 | 识别阶段 3 次重试全超时 | `FAILED` | 模块无应答，请检查波特率、TX/RX 接线 | 否 |
| 3 | 波特率不对 | 收到大量无法识别的字节（>1KB 且无合法行/帧） | 枚举 5 档重试 | 数据无法解析，正在尝试其他波特率… | 否 |
| 4 | 型号与用户选择不符 | `VERNO` 前缀与所选系列不匹配 | 暂停，让用户选"按检测结果继续/中止" | 检测到 X，你选的是 Y | 否 |
| 5 | 模块回 `ERROR` | 收到 `,ERROR,<code>` | 按 §4.5 映射；码 3 直接切能力集 | 具体原因 + 建议 | 否 |
| 6 | 回读不一致 | 查询值与下发值不符 | 重试 1 次；仍不符 → `FAILED` | 配置未生效（回读值 ≠ 写入值） | 否 |
| 7 | 无 GGA 输出 | 30 秒内有效 GGA < 3 条 | 启软件生成；仍无位置 → `FAILED` | 模块无定位输出，请检查天线和天空视野 | 否 |
| 8 | 软件 GGA 也拿不到位置 | RMC/GLL 里 lat/lon 为空 | `FAILED` | 模块没有有效定位，无法进行 CORS 标定 | 否 |
| 9 | CORS 401 | 响应含 `401` | `FAILED`，**不重试** | 用户名或密码错误 | 否 |
| 10 | CORS 404 | 响应含 `404` | `FAILED` | 挂载点不存在，请重新读取挂载点 | 否 |
| 11 | CORS 网络不通 | connect 超时/拒绝 | 3 次退避 → `FAILED` | 无法连接 host:port | 否 |
| 12 | CORS 连上但无数据 | 200 后 10 秒无 RTCM | 先发 GGA 再等；累计断连 >5 分钟 → `FAILED` | 已连接但未收到差分数据 | 否 |
| 13 | 长时间不固定 | 10 分钟内未满足准入 | `FAILED` | 长时间未进入固定解，请检查 CORS 信号/天线遮挡 | 否 |
| 14 | 采集不收敛 | 到最大时长 σ 仍 > 2cm | 让用户选：采用/延长/终止 | 精度未达目标（当前 σ=…） | 否 |
| 15 | 写坐标失败 | `ERROR` 或回读偏差 > 1mm | 重试 1 次 → `FAILED`，模块留在流动站 | 坐标写入失败 | 否 |
| 16 | 保存失败 | 无 `,OK` | 重试 2 次 → `FAILED`，**不重启** | 配置保存失败，模块未重启 | 否 |
| 17 | 重启后配置丢失 | 重启后回读值与写入值不符 | `FAILED` | 配置未能持久化，请检查模块 NVM | 否 |
| 18 | 1005 偏差过大 | 解码比对 > 0.05m | 0.05–0.5m 警告可继续；>0.5m 失败 | 模块播发的坐标与写入值相差 X m | 否 |
| 19 | 用户点终止 | `abort` 事件 | 尽快退到安全点；`SAVE`/`RESTART` 期间只标记 | 已终止，模块保持当前状态 | 否 |
| 20 | 标定中进程被杀 / 断电 | 启动钩子发现 `lease.json` 非终态 | 标记 `INTERRUPTED`，不自动改硬件 | 上次标定在 X 阶段被中断，建议重新标定 | 否 |

**贯穿全表的一条**：所有异常路径最终都回到 `release()`，而 `release()` 的第一步就是
清 `calibration_hold`，所以**主程序永远能恢复**。这是"不干扰"的底线，也是必须用
`try/finally` 而不是散落的 `except` 来实现的原因。

### 21.2 与设计不一致的九处（全部是实测逼出来的）

| # | 设计/文档原文 | 实际做法 | 原因 |
| --- | --- | --- | --- |
| 1 | `PQTMCFGRTCM` 仰角写 `-90.0`（官方示例） | 写整数 `-90` | 真机对 `-90.0` 回 `ERROR,1`；`-90` 通过。这是**唯一一处有意偏离官方示例**的命令 |
| 2 | MSM 速率按星座配（`RTCM3-1074`/`1084`/`1094`/`1124`） | 一条 `PQTMCFGMSGRATE,W,RTCM3-107X,<Rate>,<Offset>` | 真机只认 `RTCM3-107X`（全星座共用一档），按星座名或漏 `<Offset>` 全回 `ERROR,1` |
| 3 | `<Rate>` 范围 RTCM3 1~1200、NMEA 1~255 | 下限改 **0** | `<Rate>` 的定义本来就是"0 或 N，0 = 不输出"；还原必须能把标定打开的 1005 关回 0 |

| 5 | §8.5"等 `$PQTMVER` 才算重启完成" | 收不到首帧但串口**仍有数据**也算完成 | 部分固件在基站模式不打开机帧；死等会被判成"没重启"，而重试又要多等 6 秒 |
| 6 | §8.4 NVM 三态（saved / reverted / unknown） | 加第四态 `not_written` | "一条写命令都没发出去"既没保存也无从回写，混进三态会让页面写出错误的建议 |
| 7 | §0.5.5 S4"还原 = 重新走一遍标定链路" | 链路复用，但报文配置改为**按备份原样回放** | 照搬写入动作会把备份里 `RTCM3-1005=0` 改成 1：界面显示"还原完成"，实际比标定前多播一路（见 21.4） |
| 8 | 记录里存写入坐标 | `apc_*` 与 `ecef_*(ARP)` **两套都存**，另存 `ant_delta_*` | 现场"对中量到的是相位中心、模块里存的是参考点"；只存一套时，事后无法判断那 1.5 m 去哪了 |
| 9 | 备份保留多份 | 只留**最近一次**（`backup.json`） | 还原是"最后一次写入覆盖"的操作；多份只会让"到底还原到哪一版"变成一个问题，历史值在 `calibration_records` 里都有 |

另有三条写进代码的硬判据（不在上表，因为是**新增**而非**改动**）：

- **ECEF 合理性**：除单轴 ±7000 km 外，还要求到地心距离在 6000~6600 km。
  只看单轴拦不住 `(30.5, 114.3, 50)` 这种"经纬度当 ECEF"——三个分量都在合法区间，
  但到地心只有 118 m，在地核里。
- **天线偏移上限 10 m**：拦住"厘米当米"，`|U|` 现场不会超过 3 m。
- **失败不污染历史**：失败的写入只记 `calibration_events`，绝不进 `calibration_records`。

### 21.3 每一级的判据与失败处理

| 步 | 判据（源头条款） | 不通过时的处理 | NVM |
| --- | --- | --- | --- |
| `WRITE_COORD` | 回读最大轴偏差 ≤ **1 mm**（§8.2）；不一致重发一次 | 中止 | 未动，内存回写 |
| `BASE_SETUP` | 有应答即过；超时降级等重启后确认（§8.3）；`ERROR,1` 直接失败 | 中止 | 未动，内存回写 |
| `MSG_SETUP` | RTCM 档位回读必须等于目标；`RTCM3-1005` 回读速率必须为 1 | 中止 | 未动，内存回写 |
| `SAVE` | `SAVEPAR` 回 OK，且回读坐标仍等于写入值 | 中止 → **回写内存态**（§8.4） | 未写入 → `reverted`/`unknown` |
| `RESTART` | 收到开机帧，或串口仍有数据（§8.5） | 中止，**不回写** | 已保存 → `saved` |
| `VERIFY_MODE` | 重启后模式、坐标与写入值一致 | 中止，**不回写** | 已保存 → `saved` |
| `VERIFY_RTCM` | 1005 播发坐标最大轴差：≤5 cm 通过 / 5~50 cm 警告 / >50 cm 失败（§8.6） | 仅 >50 cm 中止，**不回写** | 已保存 → `saved` |
| `INJECT` | 落库失败降级为"已汇总（未落库）" | 不失败 | 已保存 |

"回写"= 只把备份里的模式与坐标重新下发到**内存**，不 `SAVEPAR`：
NVM 里本来还是旧值，再存一次会把"这次保存失败"的事实抹掉。

**GGA 的来源（这里踩过一次判断错误，必须按模式分开看）**：

- **base 模式**：协议 §2.3.25 规定基站自动禁用 NMEA、改播 `RTCM3-1005 + MSM`。
  本机实测 `GGA=0 / GSA=0 / GLL=0 / RMC=0`，15 秒监听零语句——这是**设计行为**。
  拿"base 下读不到 GGA"去推断"模块不会输出 GGA"是错的（曾据此误判，被用户纠正）。
- **rover 模式**：模块**会**输出 GGA。但"默认到底开没开"并不稳定：两次同样从
  base 切到 rover，一次读到 `GGA=1`、一次读到 `GGA=0`（受固件默认值、上次标定残留、
  NVM 是否保存过三重影响）。

结论：**代码不依赖任何默认值**。`NMEA_SETUP` 每次显式下发 `GGA=1`、`GSA=1`、
`FIXRATE=1000`，并把"配置前的实际值"记进 `result['cors_nmea']['before']` 作为实测证据。
另注意 `PQTMCFGMSGRATE` 的 `<Rate>` 语义是「**每 N 次定位输出一次**」，不是 Hz：
只配 `Rate=1` 不够，必须同时把 FIXRATE 钉到 1000 ms，否则 10 Hz 定位时 GGA 会变成 10 Hz。

**CORS 标定的第一步必须是查模式**：链路是 `get_mode() → 非 rover 才切 → 回读确认`。
CORS 的本质是"把 RTCM 喂给模块、让模块自己解算"，只有流动站成立；base 模式下模块
自己是差分源头，注入的 RTCM 不参与解算，盲目跑只会白耗 3~10 分钟拿到一堆单点解。

状态机（`run()` 的 CORS 分支，顺序即执行顺序）：

```
ROVER_SETUP → NMEA_SETUP → GGA_WAIT → CORS_CONNECT → FIX_WAIT → COLLECT → CORS_CLOSE
→ WRITE_COORD → BASE_SETUP → MSG_SETUP → SAVE → RESTART → VERIFY_MODE → VERIFY_RTCM → INJECT
```

`CORS_CLOSE` 之后的七步与历史坐标主链路**完全复用**，没有第二套校验代码。

#### 23.1.1 GGA 上报的完整时序（VRS 靠它认位置，最容易搞错的一环）

| 环节 | 实际行为 | 参数 |
| --- | --- | --- |
| **前提** | 以上一切只有在**流动站**模式下成立；base 模式按 §2.3.25 自动禁用 NMEA | 第一步 `get_mode()` |
| 模块是否自己发 | **rover 下会发**，但"默认开没开"不稳定（实测两次不一致），代码一律显式开 | `GGA=1`、`GSA=1`、`FIXRATE=1000ms` |
| 模块发多快 | 1 Hz（`Rate=1` × 1 Hz 定位） | 采集按 1 Hz 对齐，去重阈值 0.9 s |
| 代码等多久判断"模块会不会发" | 原生 GGA 专属窗口 **8 秒**；完全没位置时总等待 **30 秒** | `GGA_NATIVE_WAIT` / `GGA_TOTAL_WAIT` |
| 判"模块会发"的标准 | 收到 **3 条内容不同**的有效 GGA（按 `raw` 变化计数，防同一条数三次） | — |
| 模块会发时怎么报给 CORS | **透传原始行**，一个字段都不改（质量位/星数/HDOP 保持模块原值） | `GgaManager.source()` |
| 透传的节奏 | 仍由代码钉在 **1 Hz**：`pump()` 每 0.2 s 轮询，距上次发送 ≥1.0 s 才发 | `CorsClient.pump` |
| 模块不发时怎么办 | 从 RMC/GLL 软件生成 `$GNGGA`，**同样 1 Hz** | quality=1，星数/HDOP 取自 GSA，Sep 留空 |
| 断线重连后 | **立即补发一次**（不等 1 秒），此后回到 1 Hz | `send_gga_now` + `reset_rhythm` |

**为什么不是"逐条转发"**：代码按 1 Hz 取缓存里**最新一条**发出去。若模块 1 Hz 与代码 1 Hz
相位错开，同一条 GGA 可能被连发两次——这没问题，VRS 只关心位置，且**必须持续每秒都有上报**，
否则部分 Caster 会判定流超时并断开。反过来"严格逐条转发"会导致漏秒。

#### 23.1.2 采集、滤波、取值：每个数字到底是多少

| 环节 | 判据 / 做法 | 参数 |
| --- | --- | --- |
| 固定解准入 | **连续 30 秒**同时满足：质量=4、星数≥12、PDOP≤2.0 | `FIX_HOLD_SECONDS` |
| PDOP 来源 | 只从 **GSA** 取；无 GSA 才降级 HDOP≤1.5 并告警 | `FIX_MAX_PDOP` / `FIX_MAX_HDOP_FALLBACK` |
| 采样 | 1 Hz，按 0.9 s 去重；时长 180 / 300 / 600 秒 | `CORS_DURATIONS` |
| 野值剔除 | 3σ，滑动窗口 30，σ 下限钳到 5 mm | `OUTLIER_WINDOW` |
| 滤波 | 三轴独立 `Kalman1D`，q=1e-6，r=4e-4 | `KALMAN_Q` / `KALMAN_R` |
| **收敛判定** | 最近 **60 个合格原始样本**的 3D σ ≤ 2 cm | `CONVERGE_HOLD_SECONDS` / `CONVERGE_SIGMA` |
| **最终取值** | 3σ 剔除后的**算术平均**（`Welford3.mean`），**不是**卡尔曼状态 | — |

**为什么取值用均值、滤波只当判据**：基准站坐标是**常值量**，算术平均就是它的最优无偏估计；
`Kalman1D` 在 q=1e-6 下对静态点在毫米级上与均值等价，但它引入了模型假设（过程噪声）。
所以让卡尔曼只承担"稳定性度量"，取值交给均值更稳。两者差值记在结果的
`kf_ecef` / `kf_minus_mean_mm` 里，事后可核对滤波器有没有跑偏。

**σ 小 ≠ 坐标准**：σ 衡量的是**重复性**（同样条件下多次测量的一致性），
不含任何系统误差。CORS 基准站误差、天线相位中心偏移、多路径慢变偏差都会被
滤波当成"真值"，σ 反而更小。绝对精度的验证手段见 §23.6。

### 23.6 坐标绝对精度：本阶段**未**验证，以及该怎么验证

**先说结论**：阶段 5 产出的是**精密度**证据（重复性 σ=7.6 mm），**不是准确度**证据。
"1005 偏差 0.10 mm"只证明写入生效，不证明坐标准（见 §8.6 的语义边界）。
下面几项系统误差，σ 再小也反映不出来：

| 误差源 | 量级 | 为什么 σ 管不到 |
| --- | --- | --- |
| CORS 基准站自身坐标误差 | 参考站网级，通常 1–3 cm | 整网共模，流动站端所有观测一起偏，σ 里看不出 |
| 天线相位中心 vs 参考点（APC/ARP） | 取决于天线型号，0–5 cm | 当前 `ant_enu` 一律填 0、不扣偏移（§8.1.1 的取舍），U 向偏差会整体进高程 |
| 多路径（巷道环境） | 1–5 cm，随环境漂移 | 慢变偏差会被滤波当成"真值"，反而让 σ 看起来更小 |
| 对流层/电离层残余 | 1–2 cm | 与基线长度相关，属系统性 |

**可落地的验证手段（按可信度从低到高）**：

1. **交叉解算复测**（可自动化，约 5 分钟）
   写坐标切基站后，再把模块切回 rover、重连 CORS 解 3 分钟，比较新解均值与写入值。
   能抓：天线高/ARP 扣反、datum 用错、坐标换算 bug 这类**米级**错误。
   抓不到：CORS 共模误差。**同一套 CORS 源的自证，可信度有限。**
2. **换基准源比对**（可信度中）
   用 8001（CGCS2000）与 8002（WGS84）各解一次，或换不同 mountpoint / 不同 CORS 商。
   CGCS2000 与 WGS84 在当前精度下可视为一致，但能抓出**坐标系用错**。
3. **已知控制点比对**（可信度高）
   在同一点用已知坐标的 GNSS 控制点交叉测量。这是工程上最硬的现场验证。
4. **静态 PPP 后处理**（可信度最高，完全独立）
   采 2–4 小时原始观测（RAW），送 CSRS-PPP / AUSPOS 等在线服务解算。
   不依赖 CORS，误差源完全独立，是唯一能给出**绝对准确度**的手段。

**待办**：上述 1 可以做成 `--verify-cross` 参数（复用现有 rover/CORS 链路，只是解完不再写坐标）；
3 和 4 需要现场条件与外部服务，属操作流程而非代码。当前阶段先记在这里，未实现。
