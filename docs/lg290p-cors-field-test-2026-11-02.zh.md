## 一、测试目标

按用户要求，用标准流程把 LG290P 作为流动站接入 CORS，解算出天线的 ECEF 坐标并写入数据库：

1. 切到流动站模式
2. 配置 GGA/GSA 输出
3. 连接 CORS 并持续上行 GGA
4. 等待固定解（quality=4）
5. 1 Hz 采集 + 3σ 剔除 + 卡尔曼滤波 → ECEF
6. 写入数据库

## 三、两次正式标定运行的失败分析

### 3.1 运行 #1（17:57）

**现象**：GGA_WAIT 拿到的 GGA 是 `质量=0，卫星=0，PDOP=99.99`，FIX_WAIT 必然失败。

**根因**：`PQTMCFGMSGRATE,OK,GGA,0` —— **模块的 GGA 输出速率配置本来就是 0**。

关键点：这个 0 与 base/rover 模式**无关**。最初误判为"rover 模式不输出 GGA"，实测证伪：

```
$PQTMCFGMSGRATE,R,GGA  →  OK,GGA,0
$PQTMCFGMSGRATE,R,GSA  →  OK,GSA,0
$PQTMCFGMSGRATE,R,RMC  →  OK,RMC,0
$PQTMCFGMSGRATE,R,GSV  →  OK,GSV,1
```

显式执行 `set_message_rate('GGA', 1)` 后，rover 模式下 GGA 立即正常输出（`.probe_gga2.py`）。

**当时的代码版本**还没有"先回读 before 再配置"的逻辑，所以没有这条线索。

### 3.2 运行 #2（18:12）

**现象**：日志显示

```
[ROVER_SETUP] 当前是 base，切换为流动站
切换后 GGA 输出为 0，已显式配置为 1 Hz
FIX_WAIT 起始状态 质量=1，卫星=9,PDOP=3.06
… 180 秒后超时
最后：质量=5（需 4），卫星=21，PDOP=1.59
gga_jump_dropped=0   gga_forwarded=128+
```

**分析**：

- GGA 配置**已生效**（能读到 `质量=1，卫星=9` 说明 GGA 在输出）
- `gga_jump_dropped=0` 且 `gga_forwarded` 达 128+ → **GGA 防抖逻辑完全正常，没有误触发**
- 最终 `质量=5` 说明**差分确实生效了**，但没能推进到固定解
- 起始 `卫星=9` —— 这是模块刚重启的冷启动状态，星数还在爬升

**结论**：这次失败不是 GGA 问题，也不是防抖问题。**失败发生在差分注入之后、模糊度固定之前**。

## 四、诊断全过程与证据链

为定位"为什么停在浮动解"，逐项排除：

### 4.1 排除 CORS 账号与挂载点

```
握手响应：ICY 200 OK
源列表：22 个挂载点
可用挂载点：RTCM33_GRCEJ（其余 RTCM33_GCJ / RTCM33_GCE 返回 ERROR - MountPoint Invalid，账号未授权）
```

### 4.2 排除 VRS 距离异常

持续 30 秒上行 GGA，解析 3 条 1005 帧：

```
X = -2002015.1963   Y = 5416172.7601   Z = 2700091.8000
距本站恒定 1.056 km，30 秒内跳变 0.000 km
```

VRS 虚拟基站稳定，1.056 km 属正常范围。

> ⚠️ 过程中曾误判"VRS 的 Z 坐标错了 2024 km"。真因是探针**只发一条 GGA 就停止上行**，VRS 在缺 GGA 时输出了异常帧。这是探针调用错误，不是 CORS 问题。

### 4.3 排除卫星数量与几何精度

GSA 按星座分条输出，每条最后一个字段是系统 ID（1=GPS, 2=GLO, 3=GAL, 4=BDS, 5=QZSS, 6=其他）。
**只看最后一条会误判为"只有 2 颗星参与解算"**。逐条汇总：

| 星座 | 参与解算卫星 |
|---|---|
| GPS | 9 |
| GLONASS | 3 |
| Galileo | 5 |
| BDS | 8 |
| QZSS | 2 |
| 其他 | 2 |
| **合计** | **29 颗，PDOP=1.81** |

星数和几何构型完全充足。

### 4.4 排除 GLONASS FDMA 拖累

剔除 1084 帧后重新注入（消融实验）：

| 案例 | 注入内容 | 最高质量 | 固定解帧数 |
|---|---|---|---|
| 全集 | 全星座 | 5 | 0 |
| 剔除 1084 | GPS+GAL+BDS+QZSS | 5 | 0 |
| 最小集 | 1005+1074+1094+1124 | 5 | 0 |

**去掉 GLONASS 仍固定不了** → GLONASS 不是决定性因素。

### 4.5 排除 GGA 上行节奏问题（关键对照实验）

用一个致命细节做了 A/B 对照。**先读串口再 pump** vs **先 pump 再读串口**：

| 写法 | 150 秒 GGA 发出量 | 差分龄期 | 结果 |
|---|---|---|---|
| 先 pump 后读串口 | **1 条** | 空 | 一直 quality=2（DGPS） |
| 先读串口后 pump（**正式代码**） | **151 条** | **稳定 2.0 s** | quality=5 |

**结论：正式标定代码 `_drain_gga` → `pump` 的顺序是正确的。** 差值高达 150 倍 —— 顺序反了就等于只上报一次位置，VRS 无法持续生成改正数。

这条也反证了：在正式代码路径下，**GGA 上行和差分链路完全健康**。

### 4.6 用项目解析器核实下行数据完整性

先用错误的帧头布局统计，得出"缺 1124（BDS）"的**错误结论**。原因是把 RTCM3 帧头取错位：

| 字节 | 正确含义 | 错误理解 |
|---|---|---|
| 0 | 0xD3 前导 | ✅ |
| 1 | 保留(6) + **长度高 2 位** | ❌ 当成保留 |
| 2 | **长度低 8 位** | ❌ 当成长度高 |
| 3 | 保留(6) + 修订号(2) | ❌ 当成长度高 2 位 |
| 4–5 | **消息号(12 位)** | ❌ 当成消息号高字节 |

改用项目自带的 `extract_rtcm_frames`（带 CRC24Q 校验）后，60 秒统计：

```
消息号          帧数      Hz  说明
1005          6    0.10  基站坐标
1033          6    0.10  接收机/天线描述
1074         61    1.01  GPS MSM4
1084         61    1.01  GLONASS MSM4
1094         61    1.01  Galileo MSM4
1114         61    1.01  QZSS MSM4
1124        122    2.02  BDS MSM4
```

**CORS 播发完全正常**：五个星座全部 1 Hz MSM4，无 MSM7，共 110 颗卫星。

`1124` 看似 2.02 Hz，实际上是 **BDS 卫星太多（43 颗），每个历元拆成两帧**，两帧间隔 `0.0 ms`，聚类后真实历元率 1.00 Hz。历元对齐验证：GPS 的 30 个历元中 **30/30** 都能在 ±80 ms 内找到对应的 BDS 历元。

### 4.7 唯一的数据缺陷：缺 MT1230

上述统计中 1230（GLONASS 码相位偏差）**一帧都没有**。

这就是排除所有其他因素后剩下的唯一变量：

- GLONASS 使用 FDMA，各卫星频率不同，硬件存在码相位偏差
- 必须靠 MT1230 广播各卫星的偏差值，流动站才能把 GLONASS 纳入 RTK 解算
- 缺了 1230，模块可能**跟踪**到 GLONASS，却把它们**排除在模糊度固定之外**
- 遇到这种情况，RTK 很容易长期停留在浮动解

## 五、发现的代码问题与修复

### 问题 1：GGA 配置生效后无回读校验（中）

`_step_cors_nmea_setup` 会先回读 `before` 再配置，但**配置后没有回读确认**。
真机出现过 `PQTMCFGMSGRATE.W` 回 `OK` 但实际速率仍为 0 的情况（`.probe_nmea.py` 实测 `OK,GGA,0`）。

**状态**：本轮的 `before` 回读已能暴露大部分场景，暂不额外加回读（多一轮串口往返会干扰 RTCM 流）。**未改动**，列入后续观察项。

### 问题 2：缺 MT1230 等数据缺陷无法自动暴露（高）✅ 已修复

**现象**：300 秒卡在浮动解，所有日志都显示"链路正常、29 颗星、PDOP 1.8"，完全看不出问题在哪。必须事后手写探针数消息号才能发现。

**修复**：`rtkserver/calibration/cors.py` 新增 `DownlinkAudit` 类：

- 在 `pump()` 里对每段下行字节切帧统计（复用项目 `extract_rtcm_frames`，带 CRC 校验）
- 统计各消息号帧数、识别实际播发的 MSM4 星座
- 在 `CORS_CLOSE` 阶段输出一行体检结论
- **缺 1230 时给出明确告警**，指出这是"长时间浮动解"的优先排查项

`rtkserver/calibration/writer.py` 新增 `_audit_cors_downlink()`，接入 `CORS_CLOSE`，结果写入 `result['cors_downlink']`。

实测输出：

```
汇总：859 B/s，MSM4=GPS+GLONASS+Galileo+QZSS+BDS，1005=2帧，1230=缺失
告警：该挂载点播发了 GLONASS 观测（1084）却没有播 MT1230 码相位偏差：
      模块虽然能跟踪 GLONASS，但通常无法把它们纳入模糊度固定，
      会明显降低固定成功率。若长时间停在浮动解，请优先排查这一项
```

> 设计取舍：**只告警不终止**。缺 1230 仍有可能固定，只是成功率下降，要不要继续应由现场判断，程序不该替用户做决定。

### 问题 3：冷启动时径直进入 FIX_WAIT，白白耗尽等待窗口（高）✅ 已修复

**现象**：运行 #2 里 GGA 刚配置成功时 `质量=1，卫星=9`（模块刚重启，星数还在爬升），
流程立刻进入 FIX_WAIT，180 秒固定解等待窗口全部浪费在等搜星上。

**修复**：`writer.py` 新增 `_await_position_fix()`，在 `_step_cors_gga_wait` 之后、
FIX_WAIT 之前插入一道准入门禁：

- 等待 `channel.cache['gga']['quality'] > 0`（模块自身已定位）
- 超时 90 秒（`POSITION_FIX_TIMEOUT`），覆盖冷启动 30~60 秒的常规场景
- 每 10 秒打一次进度提示，让现场知道在等什么，而不是看起来卡住
- 超时给出四条排查方向：天线连接、冷启动、馈线通断、星座配置

**注意**：这道门禁只要求 `quality > 0`，**不要求固定解**。
质量位 1（单点）/2（DGPS）/5（浮动）都允许进 FIX_WAIT —— 差分会把模块从
单点/DGPS/浮动推向固定。要求太高反而会导致永远进不去。

`writer` 自测 21 项全部通过，含 `[19] GGA_WAIT 不误退化`（RMC 先到仍等原生 GGA）。

## 六、结论

### 6.1 能确认的

1. **标定流程代码是正确的**：模式切换、NMEA 配置、GGA 上行（151 条/150 秒）、
   RTCM 注入（900 B/s）、差分龄期（恒定 2.0 s）全部符合预期
2. **CORS 服务是健康的**：五星座 1 Hz MSM4、110 颗卫星、历元完全同步、VRS 距离 1.056 km 稳定
3. **失败点是模糊度固定**，不是链路，不是数据完整性

### 6.2 最可能的原因（按可能性排序）

| # | 原因 | 依据 | 可能性 |
|---|---|---|---|
| 1 | CORS 挂载点缺 MT1230 | 逐帧统计确认 0 帧 | **高** |
| 2 | LG290P 固件（2024/05/22）对 VRS 网络 RTK 支持不足 | 单基站 RTK 可用，VRS 不行属于典型固件差异 | 中 |
| 3 | 天线环境多路径 | 未测（需要现场观察） | 中 |
| 4 | 冷启动星数不足就开测 | 已有证据，**已修复** | 低（已修） |

其中 #1 是所有已排除项之外唯一确凿的数据缺陷。#2 无法在实验室验证，需要换固件版本对比。

### 6.3 建议的后续验证

1. **换一个播发 1230 的挂载点复测** —— 这是验证 #1 最直接的方法，成本最低
2. 若换挂载点仍不行，**升级 LG290P 固件**（2024/05/22 已接近两年）后复测
3. 同时用一台已知能固定解的设备（如和芯星通 UM980/N4）接同一挂载点做对照，隔离"模块 vs 服务端"变量
