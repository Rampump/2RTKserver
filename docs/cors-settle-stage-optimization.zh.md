## 0. 一页结论

| 问题 | 结论 |
| --- | --- |
| 一键标定和"只测坐标"是不是同一套测量逻辑 | **是，完全同一套**，只有"测完写不写"不同（见 §0.5） |
| 现在什么时候开始取值 | 固定解**连续 30 秒**就立刻开始 1 Hz 采样，没有任何观察期（`writer.py:3121-3123`） |
| 最短多久收工 | 30 秒等固定 + 60 个样本 ≈ **90 秒**就 break（`writer.py:3341`） |
| 取值怎么算 | 3σ 剔除后的**算术平均**（`writer.py:3359-3401`），卡尔曼只判稳定性、不参与取值 |
| 为什么"不精准" | 四个真缺陷：无观察期、无跳变检测、3σ 对双峰失效、收敛判据只看 σ 不看均值稳定（见 §2） |
| 双峰（相距 4 cm）会差多少 | 均值必然落在两簇中点，**偏差 ≈2 cm**，而且 3σ 一个点都不会剔（算例见 §2.2） |
| 建议怎么改 | `FIX_WAIT → SETTLE（观察不取值）→ COLLECT（分箱+跳变防护后取值）` |
| 总时长代价 | 从约 90 秒升到约 5 分钟（300 秒采集 + 120 秒观察），短档保留 180 秒快路 |
| 需不需要动代码才能验证 | 不需要。可用真机 GGA 序列做回放 fixture 先证明"当前逻辑确实偏 2 cm"（§9.1） |
| 采久一点能不能把这个漂移平均掉 | **不能**。5 cm 级散射不是白噪声，不随 1/√N 衰减（§9.4） |

## 0.5 两条路径共用同一条采集链（confirmed）

用户的选择只影响"测完之后做什么"，**测量这一段是同一个函数**：

| 环节 | 一键标定 `method='cors'` | 只测坐标 `method='external_rover'` | 证据 |
| --- | --- | --- | --- |
| 入口 | `start_cors(measure_only=False)` | `start_cors(measure_only=True)` | `service.py:616-620` |
| 计划构造 | `build_cors` → `plan.mode='base'`、`svin_mode='fixed'` | `build_cors` → `plan.mode='rover'`、`svin_mode='disabled'` | `writer.py:400-459`、`service.py:686-691` |
| 测量 | `_step_cors_collect(plan)` | **同一个** `_step_cors_collect(plan)` | `writer.py:832`、`writer.py:841` |
| 之后 | 写坐标→切基站→配报文→保存→重启→校验→落库 | 测完即止，`finally` 恢复内存模式，不写 NVM | `writer.py:833-879`、`writer.py:840-847` |
| 采集参数 | 同一份 `plan.cors['duration']` | 同一份 | `writer.py:1662-1663` |

**结论：优化只改 `_step_cors_fix_and_collect` 一处，两条路径同时生效。**
唯一要注意的是两者的"容忍度"不同：一键标定写完坐标就是这个站的最终坐标，
只测坐标往往只是"先看一眼"，所以 §4.4 给了只测的"跳过观察期"开关。

## 2. 为什么"一固定就开始取值"不准（六个缺陷）

| # | 缺陷 | 证据 | 后果 |
| --- | --- | --- | --- |
| D1 | **没有观察期**：固定解连续 30 秒就开测 | `writer.py:3121-3123` | 前段样本混着 VRS 迭代收敛期、假固定重算期，直接进均值 |
| D2 | **无跳变检测**：整簇平移不会触发任何防护 | `cors.py:93`（门限 500 m） | 4 cm 的整簇平移被当成正常数据一起平均 |
| D3 | **3σ 对双峰天然失效**：σ 用全段均值算 | `geo.py:207-233` | 两簇相距 4 cm 时两簇全在 3σ 内，一个都不剔，均值落在中点 |
| D4 | **收敛判据只看 σ，不看均值稳定** | `writer.py:3455-3474` | 单调慢漂也能判"已收敛"，还会提前 break 把样本压到 60 个 |
| D5 | **采集中失锁/重固定不重置**：只判 `accepted` | `writer.py:3266` | quality 掉到 5 再回 4 的那一段，前后样本混进同一均值 |
| D6 | **记录缺可信度判据** | `store.py:50-65` 只有 `gga_jump_dropped` | 500 m 门限下该值恒为 0，事后无法判断哪条记录该复测 |

### 2.1 补充说明：3σ 是"事后一次性"，不是流式野值检测

`reject_outliers_3sigma_xyz` 每次都用**全段均值和全段 σ** 当参考（`geo.py:218-233`），
并且 `n < min_samples` 时**原样返回**（`geo.py:215-216`），而采集侧传的是
`min_samples=OUTLIER_WINDOW=30`（`writer.py:3286`）。
所以：

- 前 30 秒（≈30 个点）**必然全部进均值**，无论它们多离谱；
- 一旦出现两簇，全段 σ 被两簇"撑大"，门限随之变宽，两簇都合法 → 剔除机制自我失效。

### 2.2 双峰算例（对应现场那 4 cm 双簇）

设两簇各占总样本一半，簇内 σ ≈ 5 mm（现场直连移动 CORS 的点云就是 5–8 mm，
见 `docs/` 之外的现场观测记录），两簇中心相距 4 cm：

| 量 | 计算 | 结果 |
| --- | --- | --- |
| 合成 σ | √(0.005² + 0.020²) | ≈ 2.06 cm |
| 3σ 门限 | 3 × 2.06 cm | ≈ 6.2 cm |
| 簇中心到合成均值 | 2 cm | **远小于门限 → 全部保留** |
| 写入值 | 两簇中点 | **偏离任一真实簇约 2 cm** |
| 末段 σ（若末 60 样本都落在同一簇） | ≈5 mm | **判"已收敛"，提前 break** |

也就是说：**当前逻辑在这种场景下会"自信地"停在上限 60 个样本并写一个偏 2 cm 的值，
而记录里的 σ 看起来还很漂亮**——这是最危险的一种失败。

### 2.3 慢漂算例（说明收敛判据为什么不够）

300 秒内位置单调漂移 2 cm，理想线性斜坡的标准差 = 2 cm / √12 ≈ **0.58 cm ≤ 2 cm**，
于是 `_cors_converged` 返回真（`writer.py:3469-3474`），
`writer.py:3341` 立刻 break，实际只采了约 1 分钟——**恰好是漂移误差最大的那一段**。

## 3. 方案 A：新增 `SETTLE` 静置观察期（观察、不取值）

### 3.1 阶段结构

```
FIX_WAIT   连续 30 秒固定解（不放宽、不改动）
   ↓
SETTLE     观察期：只看稳定性，样本不进均值
   ↓ 稳定              ↓ 不稳
COLLECT    分箱+跳变防护后取值        继续观察 / 超时给结论
```

### 3.2 判据（建议默认值）

| 判据 | 定义 | 门限 |
| --- | --- | --- |
| S1 分箱稳定性 | 每箱 20 s 算一个箱均值（3D），相邻箱均值差 | ≤ **1.5 cm** |
| S2 极差 | 观察窗口内所有箱均值的极差 | ≤ **2.5 cm** |
| S3 漂移率 | 箱均值对时间线性拟合，斜率 × 窗口长度 | ≤ **1.0 cm** |
| S4 重固定事件 | 观察窗口内 "4 → 非4 → 4" 的次数 | **= 0** |
| 窗口 | 需连续满足的观察时长 / 最长观察 | **120 s / 360 s** |

规则：

1. 任一判据不满足 → **窗口清零重来**（复用现有的"连续固定解计时器清零"思路，`writer.py:3089-3091` 与抖动容忍 `writer.py:3041-3042`）；
2. SETTLE 期间**不往 `samples` 里写任何点**，只维护箱均值环形缓冲；
3. SETTLE 超时（**360 s**，见 §6 的时间预算）**不硬失败**：降级为"环境不稳"提醒 + 继续按旧逻辑采集，并在结果里标注（保住"现场急需一个值"的场景）；
4. 浮动解路径（`FLOAT_*` 那一套）沿用同一组判据，门限放大 ~5 倍（浮动解自带 dm 级噪声）。

### 3.3 为什么是"20 s 一箱 + 三个判据"而不是只加一条"等 2 分钟"

- **纯延时挡不住跳变**：跳变可能发生在第 100 秒，延时 120 秒后照样跨簇；
- **S1 抓跳变**（相邻箱差值），**S2 抓双峰/多团**（极差），**S3 抓单调慢漂**（趋势）；
- **S4 抓"重固定"**（D5）：质量位闪一次就说明解算重来，这段时间的样本不可信。

## 4. 方案 B：`COLLECT` 改为分箱 + 跳变防护 + 只取最后稳定段

### 4.1 采集结构

| 步骤 | 做法 |
| --- | --- |
| 分箱 | 每 10 s 一个箱，箱均值进 `bins` |
| 跳变检测 | 相邻箱均值差 > `JUMP_TOL_H = 1 cm` → 记一次 `rebase_event` |
| 策略 ①（默认，保守） | **丢弃该事件前的全部样本**，从事件之后重新开始采集 |
| 策略 ②（可选，长窗口） | 保留全部样本，但精度等级降级 + 结果里标"本次含跳变，建议复测" |
| 取值 | 只用"最后一个 `rebase_event` 之后、且箱判据仍满足"的样本算均值 |
| 3σ | 降为第二道：先在**箱层**剔异常箱，再在箱内剔 3σ 点 |
| 停止 | 取消"σ 达标即 break"（`writer.py:3341`），改为"最短时长 + 稳定判据"双满足 |

### 4.2 为什么必须取消提前 break

现在的 double-break 里 `converged` 排在时长之前（`writer.py:3341-3344`），
最短 90 秒就收工。改成"最短 180 s（短档）/ 300 s（标准）/ 600 s（长档）"之后：

- 样本量从 ≈60 提升到 ≈180~600，纯噪声误差按 1/√N 再降一半以上；
- **更重要的是**：只有足够长的窗口才能容纳一次完整的分箱稳定性检验，
  否则"跳变检测"本身没有样本可比（相邻箱至少要 2 个箱）。

### 4.3 采集中失锁/重固定的处理（补 D5）

采集中一旦 `quality != 4`（或掉出 `accepted`）超过一个箱：

- 该箱标记为 `gap`，不进 `bins`；
- 恢复固定解后的第一个箱与 `gap` 之前最后一个箱做 S1 比对；
- 超过 `JUMP_TOL_H` → 按跳变处理（`rebase_event` +1）。

### 4.4 只测模式的开关

只测坐标（`external_rover`）经常是"先看一眼"，所以给一个显式选项：

| 选项 | 行为 |
| --- | --- |
| 默认（推荐） | 与一键标定**完全相同**的 SETTLE + 分箱逻辑 |
| `skip_settle=True` | 跳过观察期，直接按旧逻辑采（结果标注"未经静置观察，可信度低"） |

这个开关只影响"要不要等"，**不允许绕过跳变防护**——跳变防护是取值正确性问题，
不是耐心问题。

## 5. 取值与精度分级

### 5.1 新增输出字段（放进 `result['cors']`）

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `mean` | 最终写入 ECEF（沿用现有 `ecef`） | 写模块 |
| `tail_sigma3d` | 末段 60 样本 σ（已有） | 重复性 |
| `bin_drift` | 箱均值极差 | **双峰/漂移证据** |
| `trend_mm_per_h` | 线性趋势斜率换算成 mm/h | 判"还在不在漂" |
| `rebase_events` | 跳变次数 | 判"基准是否换过" |
| `settle_seconds` | 观察期实际耗时 | 判"环境好不好" |
| `need_resurvey` | 布尔 | 页面直接提示复测 |

### 5.2 精度分级规则（替代现在"一律 centimeter"）

现在 `writer.py:3384-3387` 只按质量位（固定/浮动）分厘米级/分米级，
**完全不看样本本身的稳定性**。建议改成两条一起看：

| 等级 | 条件 |
| --- | --- |
| `centimeter` | `tail_sigma3d ≤ 1 cm` 且 `bin_drift ≤ 2 cm` 且 `rebase_events == 0` |
| `decimeter` | 上面任一条不满足 |
| `need_resurvey` | `bin_drift > 2 cm`（双峰明显）时额外置位 |

**这两条门限（1 cm / 2 cm）不是普适常量，而是"源能力"的函数**：
同一个源静置 2.5 小时的实测散布本身就有约 5 cm（§9.4），
在那种源上 `bin_drift ≤ 2 cm` 永远不成立、`centimeter` 等级永远拿不到。
所以首次使用某个挂载点时应先做一次"源能力探测"（§9.4），
把结论作为该源的基线写进配置/记录，此后按"相对基线有没有变差"判，
而不是对每个源都硬压 1 cm。

这样一条记录能自己回答"这个站坐标到底能不能用"，而不是靠人去回忆当天天气。

## 9. 验收方法

### 9.1 回放复现（最先做，成本最低）

1. 把现场那段出现 4 cm 双簇的 GGA 序列（时间戳 + lat/lon/height/quality/sats/PDOP）存成 fixture；
2. 用一个假 CorsClient 回放给采集函数（现有自测已有先例：`writer.py:5672-5680` 用 `_FakeCorsClient` + 改小 `FIX_HOLD_SECONDS`）；
3. 断言：
   - **新逻辑**：`rebase_events == 1`，`mean` 落在**最后那个簇中心 ±5 mm**；
   - **老逻辑对照**：`mean` 落在两簇中点，与新逻辑差值 ≈ 2 cm（把"偏了"变成可复现的数字）。

### 9.2 现场复测

| 项目 | 判据 |
| --- | --- |
| 同一位置连续 3 次标定 | 互差 **≤ max(1 cm, 该源实测 repeatability)**：源本身 5 cm 级时，能量化的只有"没有变差"，不是"到 1 cm" |
| 隔 1 小时再 1 次 | 互差 **≤ max(2 cm, 该源历史 `bin_drift`)** |
| 记录字段 | `rebase_events == 0`、`bin_drift ≤ 该源基线`、`accuracy_grade` 与之一致 |

> 硬编码 1 cm 只适用于"源本身是 1 cm 级"的情况（例如直连、低时延的固定 CORS）。
> 用 5 cm 级的源去卡 1 cm，只会得到一个永远失败的验收标准 —— 那是自欺，不是严谨。

### 9.3 不回归

- `tests/` 全绿；
- `test_external_rover_only_measures` 等契约测试仍证明"只测不写"；
- 只测模式在 `skip_settle=True` 下行为与当前一致（可用来做新旧对照）。

### 9.4 精度下限由数据源决定（这一条必须先承认）

现场观测（2026-11-16，移动 CORS 挂载点 `RTCM33_GRCEJ`）：
N=8463 全为固定解、PDOP 1.08、HDOP 0.50、Age of Diff **1.9 s**，
同一台模块静置约 2.5 小时（Total Epochs 9270），
Deviation Map 在 2 cm 刻度下仍可见多个小团，整体散布 **约 5 cm**（目测推断）。

关键推论：

| 假设 | 按理论应有的表现 | 实际观测 | 结论 |
| --- | --- | --- | --- |
| 散射是白噪声（各历元独立） | N=8463 平均后误差 ≈ σ/√N，即亚毫米 | 两次静置结果相差 2~5 cm | **不成立** |
| 散射含系统性成分（改正数时延、多路径、源自身重算、天线微动） | 不随 1/√N 衰减，均值随窗口漂移 | 与观测相符 | **成立** |

所以：

1. **加长采集时间不能把这个源变成 1 cm 级**，只能把"当前这一段的中值"算准；
2. 本方案的价值因此要重新表述 —— 不是"让你测到毫米级"，而是
   **如实测出这一段有多稳、并如实标注**（`bin_drift` / `trend_mm_per_h` / `rebase_events`）；
3. 若业务上必须拿到厘米级绝对坐标，正确路径不是继续加长平均，而是换源或换方法：
   静态基线（≥4 h，指向最近的已知点）/ PPP（≥24 h）/ 已知点写入。

**"源能力探测"（建议做成一次性动作）**：首次使用某个挂载点时，用只读观测跑 30~60 分钟，
记录 `bin_drift` 与趋势，作为该源的精度上限基线写进配置；
此后每次标定的精度分级都相对这个基线判，而不是对每个源硬压 1 cm。

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 总时长 90 秒 → 约 5 分钟 | 占串口、占 CORS 账号（部分账号单并发） | 短档保留 180 秒；P0 阶段不引入观察期，先拿收益 |

## 12. 其它候选优化（按性价比排序）

除本方案的 SETTLE + 分箱判据之外，采集链上还有 4 处**低成本、证据确凿**的缺口。
它们不属于"让坐标更准"的核心，而是**让"到底准不准"可被验证、可被追溯**——
没有这几项，SETTLE 改完也只能靠感觉判断有没有变好。

### 12.1 Tier 1：建议随本方案一起做（不改产品行为，只加记录与门槛）

| # | 优化 | 现状证据 | 做法 | 收益 |
| --- | --- | --- | --- | --- |
| O1 | **用模块自报的差分龄（Age of Diff）** | `proto/nmea.py:170` 已经解析出 `age`（GGA 第 13 字段），但 `writer.py` 里**一次都没读**（grep `age` 0 命中） | 采集准入加一条 `age ≤ 2.0 s`（可配置）；`result` 里记 `age_min/median/max` | 现场实测 Age 1.9~3.2 s 正是高值；这是**现成的、免费的**链路质量指标，比事后猜强得多 |

### 12.3 明确**不建议**做的（收益低于风险）

| 想法 | 为什么不做 |
| --- | --- |

## 13. v4 重设计：采集只记录，判决放事后（真机反馈驱动）

> 本节取代 §3/§4 中"在线判据 + 跳变即清零"的部分。**标准只有一个：真机上能不能跑完、能不能给出诚实的坐标。**

### 13.1 真机上到底发生了什么（失败链，按代码定位）

用户实测（2026-11-16）：静置观察期始终进不去；采集期每约 30 秒检测到跳变、样本被清空、时长重新起算；600 秒档跑到 300~400 秒也会被一次干扰打回零；多次重试都不出结果。
日志原文："采集 68 点（剔除 1），3D σ 0.004m，72/600 秒（12%）…已丢弃 2 次跳变前的样本"。

| 现象 | 代码位置 | 实际行为 |
| --- | --- | --- |
| 观察期老在 ~30 s 被打回 | `writer.py:3417-3435` | 20 s 一箱；平移使 S1 不满足 → `settle_stable_since = None` + `trim(SETTLE_MIN_BINS)` → "连续 120 s 稳定"永远攒不够 |
| 最后一路走到 360 s 才放行 | `writer.py:3461-3480` | `SETTLE_TIMEOUT=360` 超时不失败，带"环境不稳"降级继续采 |
| 采集 68 点、72/600 秒 | `writer.py:3681-3712` | 相邻 10 s 箱均值差 > `JUMP_TOL_H=1 cm` → `samples.clear()` + `segment_started = ts` |
| "已丢弃 2 次跳变前的样本" | `writer.py:3774`（live 文案） | 两次 rebase，两次清空 |
| 300~400 秒稳定后又被打回 | `writer.py:3754`、`:3783` | 结束条件用的是 `elapsed`（**最后一段**）≥ 时长，所以一次扰动就把已积累的长样本全部作废 |

**结论：失败不是"精度要求高"，而是"一有扰动就把已完成的工作清零"。**
这个源会在一次采集内反复整簇平移（用户描述为"每次跑到 30 秒左右就跳出"；该数字的证据等级见 §19.5），
任何"清零重算"的设计都必然永远跑不完——方差再小也没用，因为样本永远攒不到时长。

### 13.2 三条根因

1. **惩罚式重置**：SETTLE 清零 + COLLECT 清空 + 时长重算，把"数据里有波动"当成"数据报废"。
2. **判决放得太早**：判据必须在采集之前/之中成立，等于要求"整段连续稳定"；而真实源的波动是间歇、周期性的，这个要求本身不成立。
3. **门限与设备能力不匹配**：`SETTLE_BIN_DIFF_MAX=15 mm`、`JUMP_TOL_H=10 mm` 是按毫米级模块设的；实际模块水平 **2~3 cm**、垂直 **2~5 cm**（1σ），源侧还有 1~5 cm 级平移，门限正好落在噪声与真实波动之间。
   注意：日志里 3D σ=4 mm 说明模块本身很稳，因此**触发的是真实的整簇平移，不是噪声误判**。

### 13.3 v4 五条原则

| # | 原则 | 对 v2 的改动 |
| --- | --- | --- |
| 1 | 采集期**只记录**：不清空样本、不重算时长 | 删掉 `samples.clear()` / `segment_started` 重置 |
| 2 | 判决搬到**事后**（SOLVE，纯计算，<1 s） | 删掉在线 S1/S2/S3 放行条件 |
| 3 | **永不失败**：最坏也给坐标 + 诚实分级 | 保留（但不再靠超时兜底） |
| 4 | **时间有界**：固定预算 + 最多一次延长 | 时长按总预算算，不看"最后一段" |
| 5 | 门限按**设备能力**（H 2~3 cm / V 2~5 cm）与实测噪声定 | 3 cm 一致集、比例门限 |

### 13.4 新时序与时间预算

```
FIX_WAIT 30s → WARMUP 60s（采样但不判决）→ COLLECT 120/180/300s（全程记录）
            → SOLVE（事后稳健求解，<1 s）→（必要时）延长一次 +120s → 结束
```

| 档 | 预算 | 最坏（含一次延长） |
| --- | --- | --- |
| 短 | 30 + 60 + 120 = **210 s** | 330 s |
| 标准 | 30 + 60 + 180 = **270 s** | 390 s |
| 长 | 30 + 60 + 300 = **390 s** | 510 s |

**永远有限**，不会像现在这样"跑到 `COLLECT_MAX_DURATION=1800 s` 才认输"。

### 13.5 SOLVE 算法（事后稳健求解）

| 步 | 做法 |
| --- | --- |
| 1 | 丢弃 WARMUP 段样本（固定 60 s，覆盖 VRS 迭代收敛期；**不做任何判据**） |
| 2 | 10 s 分箱 → 箱均值 `B_i`、箱内样本数 `n_i`、箱内 σ |
| 3 | 剔除 `n_i < 6` 的箱（数据不全的箱不进统计） |
| 4 | 稳健中心 `med` = 三轴中位数；`MAD` = `median(‖B_i − med‖)` |
| 5 | 一致集 `S = {B_i : ‖B_i − med‖ ≤ max(CONSENSUS_ABS_TOL=3 cm, 3×1.4826×MAD)}` |
| 6 | `cluster_ratio = |S| / |B|` |
| 7 | 取值：`cluster_ratio ≥ 0.6` → 坐标 = `S` 内**样本**的三轴中位数；<br>否则取 `S` 中最长连续段，段长 ≥ `LAST_SEG_MIN=90 s` → 用该段；<br>否则延长一次 +120 s 重算；仍不满足 → 全体中位数 + `need_resurvey=1` + 分级 `decimeter` |
| 8 | 同时输出 `mean_vs_median_mm`（中位数与均值的差），作为"均值是否被多簇拉偏"的诊断 |

**为什么取中位数而不是均值**（可量化）：设 70% 时间停在 A（偏移 0）、30% 停在 B（偏移 4 cm）——
均值 = 1.2 cm（偏离真实 A 达 1.2 cm），中位数 = 0（正落在 A）。
源存在周期性平移时，均值被"停留时间"加权，中位数不会。这正是当前 `writer.py:3844` 用均值的地方面临的风险。

### 13.7 精度预期（把"要求是不是太高"算清楚）

| 场景 | 水平 1σ | 垂直 1σ | 说明 |
| --- | --- | --- | --- |

| 源每 30 s 平移 1~4 cm | 1.5~3 cm | 2~5 cm | 系统性，平均压不掉（§9.4） |
| **建议验收** | **≤2 cm** | **≤5 cm** | 与设备能力对齐 |

**结论：v2 的分级要求（`tail σ ≤1 cm` + `bin_drift ≤2 cm` + 0 次跳变）在这个模块 + 这个源上不可达。**

### 13.9 验收（这次必须能过）

| 项 | 判据 |

### 14.2 P0：会直接影响"这次标定对不对/能不能用"

#### P0-1 预热到点时**不看当前是否还有点**，会把"刚好失锁"错报成"链路坏了"

`writer.py:3590-3605`：`observed >= WARMUP_SECONDS` 就 `_begin_collect(now)`，**不检查 `accepted`**。

后果链：预热第 59 秒掉出准入 → 采集时钟照开 → 这段时间采不到点 → 若失锁延续到整档结束，
`samples` 为空 → 抛 `WriteFailed('COLLECT','采集期间没有拿到任何合格样本…查账号权限/挂载点/天线')`（`:3923-3933`）。
**归因错误**：真实原因只是"交接瞬间刚好失锁"，用户会去查账号和天线。

改法（不涉及阈值）：

- 到点后要求**最近 2 秒内有一个合格点**才开采集时钟；
- 否则继续站在预热里等（最多再等 `COLLECT_BIN_SECONDS`，即 10 s），到点仍无点则按
  "从未进入采集"失败，文案写"预热结束瞬间失锁，未能开始采集"。

#### P0-2 没有"有效覆盖率"判据 → 大面积丢点会被当成"主簇 100%"

`_solve_collect` 只看到样本，不知道窗口本该多长（`:474-608`）。探针实证：

| 场景 | 求解结果 | 问题 |
| --- | --- | --- |
| 只采到 40 s 样本（窗口 180 s） | `mode=cluster`、`ratio=1.0`、`need_resurvey=False`、`converged=True` | **完全看不出只用了 40 秒数据** |

现实触发点代码自己记过：注入 RTCM 后 GGA 掉到 0.15 Hz（`:3636-3659` 的现场记录）；
此时 10 s 箱只有 1~2 点，`MIN_BIN_SAMPLES=6` 会把几乎全部箱判掉 → `len(centers)<3` → `mode=all`，
又是一句"没有主簇"，而不是"采样率不足"。

改法：

- 给 SOLVE 传 `duration`，输出 `coverage = 有效样本覆盖秒数 / duration`；
- `coverage < 0.6` → `need_resurvey=True` 且 `converged=False`，文案指明"有效样本只覆盖 x%"；
- 箱宽按实测采样率自适应：`width = max(SOLVE_BIN_SECONDS, MIN_BIN_SAMPLES / 实测 Hz)`，
  避免低采样率一律走 `len(centers)<3` 的退化分支。

#### P0-3 `JUMP_TOL_H=1 cm` 与模块标称能力不匹配 → 假平移、日志噪音、"建议复测"恒真

`writer.py:278`、`:3814-3831`、`:4035`。静态点 + 10 s 箱 + 180 s 的只读仿真：

| 模块噪声（1σ） | `rebase` 次数（已含中缝静默） | 相邻箱差中位数 |
| --- | --- | --- |
| H 4 mm / V 4 mm（**现场实测** σ=4 mm） | 0 | 2.7~3.2 mm |
| H 10 mm / V 10 mm | 0~3 | 6.8~7.9 mm |
| **H 20 mm / V 30 mm（用户标称 H2~3 / V2~5 cm）** | **7~8** | 16~18 mm |
| H 30 mm / V 50 mm | 8 | 27~29 mm |

后果：在标称能力的模块上 `rebase_events` 稳定 > `REBASE_MAX=3` → **每条记录都被标"建议复测"**，
标记失去区分力；同时 180 秒刷 7~8 条 `[REBASE]` 告警，把真正的"整簇平移"埋掉。

改法：

- 门限自适应：`jump_tol = max(JUMP_TOL_H, 3 × 相邻箱差的中位数)`（前 3 个箱定标，全程沿用）；
- `rebase_events` **只做诊断**，不再参与 `need_resurvey`（"这段数据有没有多簇"由 `bin_drift` 表达，
  它已经是箱均值极差，比"跳变次数"更直接）。

### 14.3 P1：地图对、但结论会误导用户

#### P1-1 单调慢漂被算成"主簇 100% / 已形成主簇 / 厘米级"

探针：180 s 线性漂 5 cm →

```
mode=cluster  cluster_ratio=1.0  need_resurvey=False(求解器自报)  dx=24.5 mm
bin_drift=50.0 mm（> BIN_DRIFT_WARN 20 mm，外层补设 need_resurvey=True）  trend_span=47.2 mm
```

也就是说：**外面确实标了"建议复测"，但 `converged=True`（`:3961`）**，
于是步骤说明写"已形成主簇（`:2081`）"、`on_slow='fail'` 不触发、`accuracy_grade` 仍是 `centimeter`（`:3985-3988`）。
用户看到的是"已形成主簇、厘米级"，而坐标相对窗口两端的真实偏差各约 ±2.5 cm。

改法：

- `converged = (mode=='cluster') and (bin_drift ≤ 该源基线) and (coverage ≥ 0.6)`；
- **不要再让 `accuracy_grade` 一个 key 承载两套语义**（这正是 §12 O5 的老问题）：
  新增 `coord_confidence ∈ {trusted, borderline, unfit}`，由 `cluster_ratio` + `bin_drift` + `coverage` 决定；
  `accuracy_grade` 继续只表示"固定解/浮动解"（模块质量位）。

#### P1-2 `mean_vs_median_mm` 量错了对象，作为诊断没有意义

`:597-606` 它比较的是**主簇内部**的均值与中位数，而注释写的用途是"均值是否被多簇拉偏"。
主簇内部两者本来就贴着，探针里恒为 0.4~1.6 mm；真正能证明"必须换中位数"的是**全体均值 vs 主簇中位数**。

改法：改成 `global_mean − chosen_median`（也就是"老算法会偏多少"的量化证据），
或新增 `legacy_mean_error_mm` 落库，用实际记录向用户解释为什么改。

#### P1-3 `segment_seconds` 语义自相矛盾

`:603-604`：`cluster` 分支返回 `len(centers) * width`（= 全窗口，180 s），
`last_segment` 分支返回段长（90 s）；但 `:3971` 的注释说它是"参与取值的样本实际覆盖了多长时间"。
主簇只覆盖 60 s 而返回 180 s，事后审计会看错。

改法：拆两个字段 —— `used_span_seconds`（主簇首箱→末箱 + 箱宽）、`window_seconds`（本档预算）。

#### P1-4 预热期的"失锁次数"按轮询累加，一次 2 秒失锁记成 10 次

`:3573-3578`：`settle_restarts += 1` 在**每 0.2 秒轮询**里执行一次，并且每轮都 `_stage(...)` 写同一句话。
文案"期间失锁 N 次"因此在现场严重失真，也和 `gap_events` 的口径不一致。

改法：按区间计数（进入失锁 +1、恢复时收尾），与 `gap_events` 统一；`_stage` 只在状态变化时调。

#### P1-5 精度字段的轴系标错：`raw_sample_std_e/n/u` 存的其实是 ECEF 的 X/Y/Z

完整链路（2026-11-16 复核，行号按用户落地后的版本）：

| 环节 | 位置 | 事实 |
| --- | --- | --- |
| 采样 | `writer.py:4004` | `samples.append(ecef)`，`ecef = geodetic_to_ecef(lat, lon, h_ell)` → **ECEF (X, Y, Z)** |
| 统计 | `writer.py:4170-4172` | `stat = Welford3()`；`for sx, sy, sz in samples: stat.add(...)` → 三个 Welford 分别跑在 **X/Y/Z** |
| 命名 | `writer.py:4237-4238` | `'raw_std': {'e': stat.x.std, 'n': stat.y.std, 'u': stat.z.std}`，注释称"精度评估的唯一可信口径" |
| 落库 | `writer.py:5746-5748` → `store.py:166-168` | `raw_sample_std_e / _n / _u REAL` |
| 同源 | `writer.py:4325-4328`、`kalman_std` | 滤波输出序列同样按 ECEF 轴命名成 e/n/u |

全库 `grep ecef_to_enu` 只有 `geo.py:74`（定义）与 `geo.py:446`（自检）两处，
**采集链上一个调用都没有**。

为什么这不是"命名不严谨"而是**数值错**：站心系的 Up 在 ECEF 中是
`(cos φ cos λ, cos φ sin λ, sin φ)`，于是 ECEF 的 Z 轴反分解为
`Z = cos φ · N + sin φ · U`。φ ≈ 25.2°（cos φ = 0.905、sin φ = 0.426）：

```
σ_Z² ≈ cos²φ · σ_N² + sin²φ · σ_U²
     ≈ 0.819 · σ_H²  + 0.181 · σ_V²
```

按标称 H 2.5 cm / V 4 cm：`σ_Z ≈ √(0.819×6.25 + 0.181×16) ≈ 2.83 cm`，
其中 **约 64% 的方差来自水平**（若 H ≈ V 则升到 82%）。
同理 X、Y 也是混合量（λ ≈ 110.3°E 时 `σ_X² ≈ 0.88σ_E² + 0.02σ_N² + 0.10σ_U²`，
`σ_Y² ≈ 0.12σ_E² + 0.16σ_N² + 0.72σ_U²`）——**三个轴没有一个能叫 e/n/u**。

> 注：早前口头说"90% 是水平误差"是错的。0.905 是**幅度**系数（cos φ），
> 不是方差占比。写成方差占比才对得上数值，也才对得起"精度字段"这个用途。

改法：以取值点（或首样本）的经纬度为参考 → `ecef_to_enu(dx, dy, dz, lat, lon)` →
分别算 E/N/U 的标准偏差与 RMS；输出 `raw_rms_h = √(σ_E²+σ_N²)` 与 `raw_rms_v = σ_U`，
**这才对得上"H 2~3 cm / V 2~5 cm"的口径**。

#### P1-6 记录里的 `accuracy` 取的是**全段** σ，把另一簇的间距也算进了"精度"

`writer.py:5723`：

```python
accuracy = cors.get('sigma3d')        # 注释仍写"滤波收敛后的 3D σ"
```

而 `sigma3d` 来自 `writer.py:4170-4173` 对 **全部 `samples`** 的 Welford 3D σ ——
**包含被排除在取值之外的另一簇**。旧逻辑每次跳变 `samples.clear()`，σ 只反映一簇；
v4 改成"采集只记录、不清空"之后，两簇之间那 4 cm 的间距**全部计入 σ**，
于是 `accuracy` 结构性地 ≥ 2 cm，无论选中的主簇多干净。

这是"用户感觉误差很大"最直接的技术原因之一：**他看的那个"精度"，
量的是"这段数据里两团相距多远"，而不是"写进去的坐标准不准"。**

改法：
- `accuracy` 改取 **主簇内样本**的分轴 RMS（与 P1-5 一起做，输出 `raw_rms_h` / `raw_rms_v`）；
- 全段 `sigma3d` 不要丢，改名 `source_spread` 落库 —— 它是有用的诊断量：
  两簇相距多少，一眼看出源在跳（`bin_drift` 只给箱均值的极差，这个是样本级）。

## 15. 取值方式对不对？误差为什么这么大？业界是怎么做的

> 这一节回答三个问题：(1) 我们现在这套取值方法本身对不对；(2) 现场"感觉误差大"是哪一段来的；
> (3) 常见测绘软件遇到"小范围跳动/漂移"是怎么处理的，哪些能直接抄。

### 15.1 结论：算法是对的，但它只回答"当前基准在哪"，不回答"绝对真值"

| 判断 | 依据 |
| --- | --- |
| **对**：不用均值改用主簇中位数 | 两簇各半时均值会被"停留时长"加权（70/30 → 均值偏 1.2 cm，中位数正落在主簇上）；3σ 类方法对双峰天然失效（两簇把 σ 撑大，谁都不越界） |
| **对**：判决放事后、采集只记录 | §13/§14 已实证：不再有"跑不完"，两簇场景先延长一次再兜底，永远终止 |
| **对**：固定解准入 + PDOP + 差分龄记录 | 与业界一致（见 15.3） |
| **不对**：用"结构指标"冒充精度 | `converged = (mode=='cluster')` 会让 5 cm 慢漂也报"已形成主簇"（§14 P1-1）；精度必须分轴、分 RMS |
| **不对**：验收尺子本身错了 | 我们曾要求 `σ ≤1 cm` + `箱漂 ≤2 cm` + `0 次跳变`，而模块标称 H2~3 cm / V2~5 cm、源还有 1~4 cm 平移 —— 三个条件不可能同时满足，于是每次都"不合格"。**问题不是坐标错，是尺子错** |

一句话：**这套方法算的是"这段数据里哪一簇代表当前生效的基准"**。
做基准站，要的正是这个（播出去的坐标必须和当前改正数一致）；
但它**不能**告诉你"这个点在地球上的绝对坐标是多少"——那由源决定，算法补不了（§9.4）。

### 15.2 误差预算：3 分钟里哪些能压、哪些压不掉

| 项 | 量级 | 能不能靠平均压掉 |
| --- | --- | --- |
| 模块单历元噪声（标称） | H 2~3 cm / V 2~5 cm（1σ） | 能：180 历元后随机项 ≈ 2~3 cm / √180 ≈ **1.5~2.2 mm** |
| 现场实测短段离散 | 3D σ **4 mm**（真机日志） | 已经很干净，说明模块本身没问题 |
| 源整簇平移（每 ~30 s，1~4 cm） | 1~4 cm | **不能**：它是系统性，不是白噪声（2.5 h 测 8463 个点仍散 5 cm 就是证据） |
| 天线多径（~10 cm 蘑菇头） | cm 级 | 不能，只能靠硬件/选址 |
| **因此单次 3 分钟的绝对精度上限** | **H 1~3 cm、V 2~5 cm** | 这就是物理上限，换个算法也突破不了 |

所以"感觉误差大"有两层原因：
**(a) 尺子错**——我们把门槛定在 1 cm 级，任何一次都判不合格；
**(b) 方法错位**——拿"3 分钟实时点的重复性"去当"基准站成果坐标"，而成果级坐标在测绘行业里从来不是这么定的（见 15.3）。

### 15.3 常见测绘软件怎么处理这种"小范围跳动/漂移"

分四层，每层的目标不同，**没有一层是靠"更聪明的滤波器"**：

**① 实时点测量（地形点/碎步点）——靠"容差 + N 历元平滑"**

| 软件 | 做法 | 关键参数 |
| --- | --- | --- |
| Trimble Access | 用户设 `Horizontal tolerance` / `Vertical tolerance`，只有**落在容差内的历元**才计数并参与平均；QC1 记录"容差内历元数、最大 DOP、RTCM Age、告警" | 容差可自动按接收机 RTK 规格与基线长算；可选"仅存已初始化解" |
| 千寻 SR2 / 星矩 | 采点记录条件：固定解、`H 0.05 m`、`V 0.10 m`、`PDOP 3.0`、`延迟 5`、`平滑 1`；控制点测量把"测量次数"改 5 | **注意：业内默认容差是 H 5 cm / V 10 cm**，比我们严得多地要求 1 cm |
| 南方 / 千寻 产品指标 | RTK：H 8 mm+1 ppm、V 15 mm+1 ppm；**静态：H 2.5 mm+0.5 ppm、V 5 mm+0.5 ppm** | 同一台机器，静态与 RTK 差一个数量级 |

关键点：它们把"落差"放在**容差**上（超容差的历元直接不计），不是放在"事后算法"上。
我们现在的 3D 3 cm 一致集，本质上比"平滑 1 个历元"更严，不是更松。

**② 控制点/跨站重设——靠"独立复测互差"**

千寻 SR2 手册明确：跨站重设/点校正完成后**必须复测其他控制点**，
与已知坐标比对一致才算完成；点校正的水平残差要求在 2 cm 内。
Trimble 的 RTX-RTK offset 文档也强调"用同一位置的精确 RTK 点与精确 RTX 点求差"。

→ **这就是行业对"跳变"的正解**：跳变是系统性误差，滤波只会把它平滑到两簇中间；
唯一有效的办法是**换时段/换几何/换源再测一次，看互差**。互差 ≤2 cm 才算可用。

**③ 成果级坐标（控制点、基准站）——不用实时平均**

等级稍高的坐标走静态观测 + 基线解算（到已知 CORS 点）或 PPP，
精度 H 2.5 mm+0.5 ppm 级 —— **观测时长决定精度，不是采样率**。
这正是之前讨论过的 RTKLIB `rnx2rtkp` / CSRS-PPP 路线。

**④ 基准站坐标本身**

行业做法是：用**已知点**（有实测坐标的标志点）、**长期静态/PPP** 定，
或者用接收机自带 survey-in 自收敛（本质也是平均，而且明确标注为"未实测等级"）。
用"临时 RTK 平均"给基准站定坐标，只在"米级够用、用来给 RTCM1005 起个初值"的场合成立。

### 15.4 我们缺的三个行业动作（都能直接补进现有流程）

| # | 缺什么 | 为什么重要 | 怎么补 |
| --- | --- | --- | --- |
| 1 | **H/V 分轴容差**（现在是 3D 距离 3 cm 一刀切） | 垂直本来就比水平差一倍（V 2~5 cm vs H 2~3 cm），用同一个 3 cm 球形容差会把"垂直散布"误判成"两簇" | 容差改成椭球：`‖dE,dN‖ ≤ CONSENSUS_H`、`|dU| ≤ CONSENSUS_V`；箱距离也分轴算 |
| 2 | **容差内历元计数**（只有"箱内样本数"） | Trimble 的质控口径就是"落在容差内的历元数"，这才是可交付的"观测质量"证据 | SOLVE 输出 `epochs_in_tol / epochs_total`，落库 |
| 3 | **复测互差检核**（完全没有） | 这是唯一能发现"源整体偏移"的手段；单次结果再漂亮也证明不了绝对正确 | 记录里存 `last_ecef` 与 `repeat_delta_mm`；同一 SN + 同一位置再次标定时自动算互差，> 2 cm 就提示"无法判定哪次对" |

### 15.5 想真正把误差做小，三条路（按性价比）

| 路线 | 动作 | 预期收益 | 成本 |
| --- | --- | --- | --- |
| A. 软件/流程（零硬件成本） | 15.4 的三条 + §14 的 P1-5 轴系修正 + 验收改 H≤2 / V≤5 cm + 界面显示真实 H/V RMS | 不再"每次都判不合格"；用户拿到诚实的数，而不是假的好看数 | 一两处代码 |
| B. 数据（前面讨论过的静态路线） | 采集期把 **RTCM 原始流落盘** → 转 RINEX → RTKLIB 静态基线解到几十 km 内 CORS 已知点；或 24 h PPP | H 5~8 mm、V 1~2 cm（比实时 RTK 好一个数量级） | 需要落盘与离线解算（对应 §12 O2 未做项） |
| C. 硬件/选址 | 换小天线或加地平面/扼流圈，避开天线正下方反射面；天线离墙/金属面 ≥1 m | 直接砍掉多径那 1~2 cm（现场 4 cm 双簇多半有它的份） | 现场施工 |

### 15.6 建议的验收口径（替换 §9.2 的 1 cm）

| 项 | 判据 |
| --- | --- |
| 单次水平 | `raw_rms_h ≤ 2 cm`（且 ≤ 该源实测 repeatability） |
| 单次垂直 | `raw_rms_v ≤ 5 cm` |
| 结构 | `cluster_ratio ≥ 0.6` 且 `coord_confidence = trusted`（§14 P1-1） |
| 覆盖率 | `coverage ≥ 0.6`（§14 P0-2） |
| **绝对可信** | **两次独立复测互差 ≤ 2 cm**；否则一律标"未通过检核，仅作初值" |

## 16. 参照：RTKBase 的基准站坐标是怎么来的

> 用户问"rtkbase 他们的标定方式是怎么弄的"。结论很直接：**RTKBase 没有"标定"这个功能**。
> 它把"基准站坐标从哪来"这件事整个推到了离线流程里，自己不碰。这一点和我们现在的"一键标定"是两个物种。

### 16.1 RTKBase 的架构（决定了它能做什么、不做什么）

RTKBase = Web 前端 + bash 脚本 + systemd 服务，底层全套依赖 **RTKLIB**（`str2str` / `rtkrcv` / `convbin`）。
前端能力清单里与坐标相关的只有两条：

- **"Edit the services settings"** —— 设置页里手填基准站坐标（`lat / lon / height`）；
- **"Convert raw data to Rinex"** —— 把记录的原始观测转成 RINEX，**交给外部工具去算坐标**。

README 里那句关键的话（原文意思）：

> "The settings page allows you to enter your own settings for the **base coordinates**..."
> "**If you don't already know your base precise coordinates**, it's time to read one of these tutorials:
> rtklibexplorer – Post-processing RTK（静态基线） / rtklibexplorer – PPP（双频接收机）"

也就是说：**RTKBase 的坐标来源只有两条 —— 离线静态基线解算，或离线 PPP。**
它甚至不提供"采 3 分钟平均一下"这种功能；它认为那不是标定。

### 16.2 行业里"标定/定坐标"的四种正规做法（都是离线或外部）

| 做法 | 典型参数 | 绝对精度 | 谁在这么干 |
| --- | --- | --- | --- |
| **① 已知点手输** | 有实测坐标的标志点（PSM） | 取决于标志点本身 | Trimble / Emlid / RTKBase 都支持；Emlid 还有 Base shift 用已知点反算平移 |
| **② 静态基线解算** | 记录几小时 RINEX，就近取 CORS/IGS 已知站做基线 | 优于 1 cm | **RTKBase 官方指路**、rtklibexplorer 教程、SparkFun 永久站流程 |
| **③ PPP** | 24 h 原始观测（1 Hz 即可），CSRS-PPP / OPUS / gLAB | 水平 ±2 mm、高程 ±8 mm 级（报告给 95% 置信） | SparkFun 永久站、Emlid（明确写"**无需实时差分、无需附近基准站**"）、RTKBase 教程 |
| **④ Survey-in（接收机自收敛）** | 最短 60 s、3D 标准差门限常配 **5.00 m**；Quectel 建议 **43200 s（12 h）** 才叫精确 | **只保证相对精度**，绝对值可能差几十 cm | u-blox F9P、SparkFun、Quectel LC29HBS |

注意第 ④ 行那两个数字：**行业默认的 survey-in 门限是"米级"，最短时长 60 秒是给"临时基站"用的**；
要精确就明确要求跑 12 小时。**"3 分钟出 cm 级成果"在行业里没有对应做法。**

另外 SparkPNT 给了一个很聪明的中间档 —— **Augmented Survey-In**：
先把流动站架在三脚架上、用 CORS 拿到固定解，再切到 survey-in 让它在"带差分的状态"下平均 60 秒。
实测日间变化 50 mm RMS、与同日 PPP 相差 65 mm。这基本就是我们"一键标定"想做的东西的正确定位：
**不是成果坐标，是"能用的初值"**。

### 16.3 和我们的"一键标定"对照

| 维度 | RTKBase | 我们（v4 现状） |
| --- | --- | --- |
| 坐标怎么来 | 外部算好 → 手填 | 设备内实时 GGA → 3 分钟主簇中位数 |
| 有没有"标定"这个词 | 没有 | 有，且做成了一键流程 |
| 精度承诺 | 不承诺（取决于你填的数） | 曾承诺 1 cm（§9.2，已由 §15.6 替换） |
| 关键前置 | RINEX 落盘 + 外部解算 | **没有落盘**（§12 O2 未做）→ 无法离线复算 |
| 1005 播发 | 用你填的坐标 | 用求出来的坐标（无法追溯真值） |

### 16.4 由此得出的三条明确结论

1. **"一键标定"这个名字要改**。它做的是"读取接收机当前 RTK 位置并稳健取值"，
   在测绘语境里这叫 **position / 初值**，不叫标定（survey / calibration）。
   建议 UI 与文案统一叫「取当前位置（初值）」，并在结果里注明"绝对精度取决于数据源"。
2. **真正的标定必须离线，且必须先有落盘**。RTKBase 能做厘米级是因为它把 RINEX 交出去；
   我们没有落盘，就永远只能做"初值"。这直接指向 §12 O2（原始观测/RTCM 落盘）—— 它是所有高精度路线的前置，
   优先级应该从现在的位置往上提。
3. **保留一键标定，但把它的价值定位在"让 1005 有个像样的初值 + 可复测的稳定性证据"**：
   - 初值：H 1~3 cm / V 2~5 cm（§15.2 的物理上限），完全够 1005 用；
   - 证据：`coord_confidence` + 两次复测互差（§15.4 第 3 条）；
   - 升级路径：同一个天线位置跑 ≥2 h 静态 → RTKLIB 基线/PPP → 把成果坐标**手填/回填**进配置，
     这才是成果级。

## 19. 通俗版：现在这个坐标到底是怎么算出来的

> 给不看行号的人看。一句话：**采集的时候什么都不判，只把点攒下来；采完再一次性开会，吵出"你天线常站哪儿"。**

### 19.1 六步走

| 步 | 程序在干什么 | 为什么这么干 |
| --- | --- | --- |
| **0 等固定解** | 一直等到模块连续报固定解（FIX_WAIT） | 浮动解是米级，采它没意义 |
| **1 预热 60 秒** | 这 60 秒的点**全部扔掉**，一个都不参与取值 | 刚锁定那一段质量最差（残差还在收敛、大气改正刚换、接收机还在稳），拿它算就是拿最脏的水当样本 |
| **2 采集 120 / 180 / 300 秒** | 每秒收一个点，**只记录，不判断好坏**。中途跳变只记一条"整簇平移"事件，**样本一个都不清** | 老逻辑一跳变就清空重算，而你这个源在采集期内会反复跳（你描述约 30 秒一次，待实测）—— 所以永远跑不完 300 秒。现在跳变不影响采集继续 |
| **3 事后分箱** | 10 秒一箱，每箱算一个平均点 → 180 秒 = 18 个"箱中心"；箱里不足 6 个点的箱直接作废 | 单点噪声大，先按箱平均压一遍，后面比较的是"每 10 秒这套系统整体站在哪" |
| **4 找主簇** | 看箱与箱之间离多远，定一个容差（≥3 cm，且随本段噪声自适应）→ 找"邻居最多"的那个箱当种子 → 把容差内的箱全圈进来 → 得到"主簇" | 你的数据往往是两团甚至几团。"哪一团才是天线的真实位置"不能靠平均投票，得先看哪团人多、哪团密 |
| **5 取值** | **取主簇里所有原始点的中位数**（东、北、天各取中位数），不是平均值 | 平均值会被"停留时间"加权（在 A 待 60 秒、在 B 待 120 秒，均值就偏 B），也会被偶尔窜出去的野点拽走；中位数只回答"最常出现的位置" |
| **6 体检** | 三票：①主簇占全部箱 ≥60%；②箱均值极差没超过本段噪声基线；③合格箱覆盖了窗口 ≥60%。三票全过标 `trusted`，缺一票 `borderline`，没主簇 `unfit`，都要不要标"建议复测" | 坐标照给，但**必须同时给"这坐标可不可信"**。老版本只给一个 σ，两团相距 4 cm 时 σ 永远 2 cm，看上去每条都不合格 |

两团各半、谁也压不倒谁的时候，还有两级退路：先**延长 120 秒**再判一次（样本不清，接着采）；
延长后仍分不出主簇，就取"最后一段连续 ≥90 秒的一致段"；连这段都没有，才退回全体中位数，
并把可信度打成 `unfit` + "建议复测"。

### 19.2 拿你那台机器走一遍

你的源大致是"每隔几十秒整簇挪 4 cm"（30 秒来自你的描述，**不是实测出来的**，证据等级见 §19.5）。
按 30 秒计，180 秒里大约 9 箱在 A、9 箱在 B：

- 主簇比 = 50% < 60% → 不算主簇；
- 最长连续段 = 30 秒 < 90 秒 → 也退不到 last_segment；
- 于是延长 120 秒再算，还是五五开；
- 最终落在 `all`：坐标 = 全体中位数 ≈ **两团的正中间**，离任一簇约 2 cm，标 `unfit` + 建议复测。

这不是算法算错了，而是**这类源本身没有"唯一正确坐标"**：它在两个位置之间来回跳，
任何算法都只能给你其中一个、或者两者中间，并且告诉你"这次不算数"。
真正能提升的只有两件事：换更稳的源，或者用静态/PPP 离线解（§15、§16）。

### 19.3 精度数字现在代表什么（§18.1 已落地后的口径）

- **`raw_rms_h` / `raw_rms_v`** = **参与取值那批样本**（主簇内）的东-北合成 / 天向离散度
  → **这才是"你写进去的这个坐标有多准"**。

- 两团各占一半、判不出主簇时：坐标本身就是两簇中点，`accuracy` 照样大，
  但同时 `coord_confidence=unfit`、`need_resurvey=1` —— **这是诚实的"没把握"，不是 bug**。

   所以只能读到"约 30 秒 / 约 40 秒"，读不到精确秒数。
3. **现成但粗：`result['rebase_times']`**
   同样的数据已经进了结果字典（`writer.py:4080`），只是**没落库**（见 §17.3 ⑥）。

还有一个比"周期是几秒"更有价值的判别：

- 若每次重试的**第一次**跳变都出现在"自己连上之后 ≈30 秒"→ 是**连接后固定触发一次**的服务端行为
  （VRS 重算 / 中继健康检查），**不是源有全局的 30 秒周期**；
- 若跳变时刻相对你的连接时刻是**随机分布**（有的 10 秒、有的 25 秒）→ 才是源侧的准周期现象。

这两种解释对应完全不同的根因、也对应完全不同的修法，建议先分清再动手。

## 20. 「整簇平移」到底按什么判（判定链 + 局限 + 一个真缺陷）

> 这一节只描述**现在的代码怎么判**，以及它判不准的地方。方案在 20.5，代码未改。

### 20.1 判定链：四步，没有第五步

| 步 | 做什么 | 位置 |
| --- | --- | --- |
| 1 **分箱** | 第一个合格点开箱，之后每来一个点、距箱起点 ≥ **10 秒**就闭箱；箱值 = 箱内样本的**三维均值** | `writer.py:386-407`（`_BinTracker.add` / `_close`） |
| 2 **算相邻差** | `last_diff` = 最后两箱均值的**三维距离** `√(Δx²+Δy²+Δz²)` | `:432-437` |
| 3 **定门限（一次）** | 箱数满 3 时用 `step_median`（所有相邻箱差的中位数）定标：`jump_tol = max(1 cm, 3 × step_median)`，**锁死不再变** | `:4135-4144`、`:439-452` |
| 4 **判事件** | `jump > jump_tol` 且不在冷却期 → `rebase_events += 1`、记 `rebase_times`、打告警与日志 | `:4145-4160` |

两个关键量：

- `JUMP_TOL_H = 1 cm`（下限）、`JUMP_TOL_FACTOR = 3.0`、`JUMP_TOL_LOCK_BINS = 3`（`writer.py:320-322`）
- 冷却：`rebase_mute_until = ts + 2 × 箱宽`（20 秒，`:4160`）。原因是**跨平移的那一箱均值落在两簇中间**，会让下一个箱再触发一次同向差，静默两箱避免"一次平移记两次"。

**最重要的一句：这一步只记录，不清样本、不重算时长、不参与取值、不决定成败。** 老逻辑的清空重算就是"永远跑不完 300 秒"的根因，v4 把它彻底去掉了。

### 20.2 门限为什么必须自适应

固定 1 cm 对不同模块的意义完全不同：

| 本段噪声（相邻箱差中位数） | 自适应门限 `max(1cm, 3×)` | 180 秒（18 箱）里会误报几次 |
| --- | --- | --- |
| 3 mm（干净源） | 1 cm | 0 次 |
| 17 mm（H2–3 cm 的模块） | 5.1 cm | 0 次 |
| 固定 1 cm 去打 17 mm 的源 | 1 cm | **实测 7~8 次**（全部是噪声，真平移被埋掉） |

这就是 P0-3 的由来：门限得先量出"这台机器自己的抖动有多大"，再拿它当尺子。

### 20.3 三条局限（设计如此，但要知道）

1. **只看"相邻一箱"，所以慢漂永远不触发。**
   每箱只挪 0.7 cm、18 箱累计 4 cm 时，相邻差一直小于门限 → `rebase_events = 0`。
   这类由另一条线兜：`bin_drift`（箱均值极差）对 `drift_limit = max(2 cm, 8×step_median)`（`writer.py:330-334`、`:515-532`）。
2. **前 3 箱定标可能被真平移污染。**
   若前 3 箱里恰好发生一次 4 cm 平移，`step_median` 被抬到 4 cm → 门限变 12 cm → **之后所有 4 cm 的平移全部漏检**。现在没有任何防护（既没去极值，也没用 MAD）。
3. **10 秒箱宽 + 20 秒冷却 = 分辨率损失。**
   平移落在箱中间时，那一箱均值只挪半个位移（2 cm），门限 3 cm 就会漏；反过来，20 秒内发生两次跳变会被吞成一次。

### 20.4 一个真缺陷：数据空洞会破坏"相邻"这个前提

`add()` 只在**有合格点**时被调用，掉线/失锁期间不闭箱。

后果：空洞前后的两箱可能相隔几十秒（箱中心 = `_cur_start + width/2`，事件驱动、不与墙钟对齐），
但 `last_diff` 仍把它们当"相邻箱"比较 —— 这中间的正常漂移（尤其被 VRS 换点放大）会**被记成一次"整簇平移"**。

而 `gap_events` 的统计与这条判定**完全没有联动**（`:4081-4089` 只打日志、只计数）。

所以日志里一条 `[REBASE] 整簇平移 XX mm` 有两种可能，**从日志本身分不开**：

- 真的基准换了（VRS 重算 / 换主站 / 中继切源）；
- 掉线一段时间后复现，跨空洞的正常漂移被当成一次跳变。

### 20.5 建议的防御性改法（只写方案，未改代码）

最小改动、不动任何判定行为，只补一句前提检查：

```python
# 伪代码，位置：writer.py:4145 的 if closed and ts >= rebase_mute_until 之后
prev_center, cur_center = collect_bins.bins[-2][0], collect_bins.bins[-1][0]
spanned = cur_center - prev_center
if spanned > COLLECT_BIN_SECONDS * 2:        # 不是"相邻"，是跨空洞
    # 方案 A：跳过比较，单独记成 gap_shift（不冒充整簇平移）
    # 方案 B：把空洞后的第一箱当作新段起点，不参与与空洞前的差
```

配套两条（可选，按需要）：

- **局限 2**：定标从"前 3 箱"改为"前 3 箱去掉最大一个再取中位数"，或延到第 6 箱再定一次标（避免被开局的一次真平移带偏）；
- **局限 3**：若一个采集里 `rebase_events` 与 `bin_drift/step_median` 的比值异常（例如事件数 > 箱数/3），说明门限定标失效，落一个 `jump_tol_doubt=1` 标记让人复查。

### 20.6 两套机制分工（别把"跳了几次"当结论）

| 字段 | 含义 | 影响坐标吗 | 影响"能否使用"吗 |
| --- | --- | --- | --- |
| `rebase_events` / `rebase_times` | 采集期检测到几次"相邻箱整簇挪动"，各在第几秒 | 不影响 | **不影响**（纯诊断） |
| `bin_drift` vs `drift_limit` | 箱均值极差是否超出本段噪声基线（慢漂/多簇都算） | 不影响 | **影响**（进入 `need_resurvey`） |
| `coverage` | 合格箱覆盖窗口的比例（≥60%） | 不影响 | **影响** |
| `cluster_ratio` | 主簇占全部箱的比例（≥60%） | 影响取值方式 | **影响** |

也就是说：`rebase_events = 0` 也可能因慢漂被判 `borderline`；`rebase_events = 5` 只要主簇仍够 60%，坐标照样 `trusted`。

### 20.7 落库现状

只有 **`rebase_events`（次数）** 进了库（`store.py:55,265`）。

`rebase_times`（每次发生在第几秒）、`gap_events`（空洞区间）、`jump_tol`（当时的门限）
都只活在 `result` 字典与日志里（`writer.py:4434-4440` 附近），**没有对应的库列**。
所以想复盘"这次是哪几次跳、跳了多少"，只能翻服务器日志里的 `[REBASE]` 行。
